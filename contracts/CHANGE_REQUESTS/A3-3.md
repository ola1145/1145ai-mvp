# A3-3: what the copilot's proposals need from proposeChange (owners: T2 `services/tool-api/src/lib/changes.ts`, C0 contract, C1 router)

**From:** [1145:A3] owner copilot · **To:** T2 (propose/apply), C0 (`contracts/openapi/tenant-tools.yaml`), C1 (router payload)

`agents/admin/tools.py` now sends the payloads `normaliseChange` validates, relays the server's `summary` word for word with the
code (SEC-21, enforced by `common/runtime.py enforce_relay`), and refuses to relay anything without a summary and one 4-digit
code. Two kinds of change still can't succeed from chat, and the copilot says so honestly ("I can't set that one up from chat
just yet ... You can make that change in the dashboard") until these land. Additive only.

## 1. T2: service changes by name
The copilot has no read that returns service ids (admin-agent can't list services), so it can't send `serviceId`. It sends:

```json
{ "kind": "service", "payload": { "serviceName": "Beard trim", "priceCents": 2500 } }
```
(`durationMin` and `active` the same way, only the fields that change.) Proposed in `normaliseService`: when `serviceId` is
absent and `serviceName` is present, resolve it among the tenant's `SERVICE#` items, case-insensitive and whitespace-trimmed;
store the resolved `serviceId` in the payload as today. No match: `404 unknown_service` (the copilot already asks "Which one did
you mean?"). More than one: `409 ambiguous_service` with a `sayToCaller` naming the choices. The summary stays generated from
the stored service, so what the owner confirms is still the real change.

## 2. T2: hours without a timezone keep the stored one
The router doesn't send the tenant's timezone yet (A1-2 section 1, C1). Guessing one would move every booking for a tenant
outside it, so the copilot sends `{ "weekly": [...] }` with no `timezone` when it doesn't know it. Proposed: `timezone` optional;
when absent use `HOURS.timezone`, then `PROFILE.timezone`; `400` only when neither exists. When the router does send it, the
copilot includes it and nothing changes.

## 3. T2 (nice to have): don't make owners retype the week
An hours proposal replaces the whole week, and the copilot can't read the current hours, so "make Saturdays 10 to 4" costs the
owner one extra message ("What are your hours the rest of the week?"). Either of these removes it:
- `GET /v1/admin/hours` for `admin-agent` (returns `HOURS`), or
- a per-day patch: `{ "kind": "hours", "payload": { "days": { "6": [{ "open": "10:00", "close": "16:00" }] } } }` merged into the
  stored week, with the summary describing the whole resulting week.

## 4. T2: price changes and the code
For `requiresStepUp`, `messageForOwner` says "open the app to confirm it" with no code, and the router answers `CONFIRM <code>`
for a price change with the step-up line. The copilot tells the owner "Reply CONFIRM 5307, then approve it in the dashboard" so
the owner has the code if the dashboard asks for it. If the dashboard lists pending changes without a code, say so and the
copilot will drop the code for step-up changes.

## 5. C1: `timezone` in the copilot payload
Still open from A1-2 section 1: `{ ..., tenantToken, timezone }` (IANA, `PROFILE.timezone` else `HOURS.timezone`). The admin
entrypoint passes it to the tools only when it's a real zone.
