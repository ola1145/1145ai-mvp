# C3-2: let the router echo `clientMessageId` as `inReplyTo` on owner chat replies (optional)

**From:** C3 (owner web chat API) · **To:** C1 (router: `services/channels/src/router.ts`, `lib/senders.ts`)

## Why
`contracts/realtime/channels.md` says owner chat replies carry an optional `data.inReplyTo` equal to the `clientMessageId` of the message
being answered, and `createOwnerChatPublisher` already accepts `meta.inReplyTo`. Today `createSender` calls
`publishOwnerChat(to.channelUserId, text)` without it, because `ReplyTarget` has no message id. C3 puts the owner's `clientMessageId` in
`InboundMessage.channelMessageId`, so the router already has it.

## Proposed change
1. Add `channelMessageId` to `ReplyTarget` (`Pick<InboundMessage, 'channel' | 'channelUserId' | 'chatId' | 'channelMessageId'>`) and fill it in `target(msg)`.
2. In `createSender`, for `webchat`: `deps.publishOwnerChat(to.channelUserId, text, { inReplyTo: to.channelMessageId })`.

Holding lines and the agent's real reply would both carry the same `inReplyTo`, which is what the app wants (it can clear its "typing" state on the first reply
and keep appending). Nothing in C3 depends on this; the app works without it, it just cannot tie a reply to the message that caused it.
