# H1-1: control-plane stack needs for the Stripe webhook, and what H2 can now drop or update

**From:** H1 (Stripe webhook, billing state, audit writer) **To:** H2 (owns `infra/cdk/lib/controlplane-stack.ts` and `src/console/**`) **Status:** open, not blocking (H1 is tested against fakes)

## What
1. The `StripeWebhook` function in `controlplane-stack.ts` needs env, a secret grant and DynamoDB access. Today it has none of the last two, so it cannot verify or write anything once deployed.
2. H1 now exports the shared audit writer H2-1 asked for. `console/audit-sink.ts` can be deleted.
3. `setTenantState` changed order. One line in `console/README.md` is out of date.
4. One field name differs between the console's event and the event schema.

## 1. Infra for `StripeWebhook`
Entry is `services/control-plane/src/stripe-webhook.ts` (handler `handler`). It already gets `TABLE_NAME`, `EVENT_BUS_NAME`, `AUDIT_BUCKET`, `TENANT_BUCKET`, `auditBucket.grantPut` and `grantPutEventsTo`. Add:

- Env `RUNTIME_SECRET_ID = 1145/<stage>/runtime` (the secret the router already reads, as in `channels-stack.ts`; the key is
  `STRIPE_WEBHOOK_SECRET`, pushed by `scripts/secrets/push.sh`) and read access to that secret:
  `sm.Secret.fromSecretNameV2(this, 'RuntimeSecret', <the same name>).grantRead(stripe)`.
- Env `STRIPE_LIVEMODE`: `'false'` in dev, `'true'` only on the stage that takes real money. Unset means test mode, so a missing value fails safe: live events get 400 `wrong_mode` instead of being acted on.
- KMS: `table.encryptionKey?.grantEncryptDecrypt(stripe)` (the table uses a customer-managed key).
- DynamoDB, named actions only, each with a `dynamodb:LeadingKeys` condition (no `dynamodb:*`, no Scan):
  - `GetItem`, `UpdateItem` on `TENANT#*` (profile read, billing marker, state) and `UpdateItem` on `NUMBER#*` (route state, via `consoleEngineFor`);
  - `PutItem`, `GetItem`, `UpdateItem`, `DeleteItem` on `STRIPEEVT#*` (event ledger);
  - `GetItem` on `STRIPECUST#*` (customer to tenant route).
- The tenant bucket needs no grant for the webhook (the env is only read, never used).
- Worth asserting in `infra/cdk/test` (see H2-3): `/stripe/webhook` stays `AuthorizationType: NONE` (the signature is the credential), and the Stripe role has no `dynamodb:Scan`.

## 2. Delete `console/audit-sink.ts` (answers H2-1)
`services/control-plane/src/audit.ts` now exports:

```ts
export interface AuditEntry { tenantId; action; reasonCode; actor; at; requestId?; supportCaseId?; note?; detail? }
export function auditKey(e: Pick<AuditEntry, 'tenantId' | 'at'>, id?: string): string
export function auditWriter(s3: Pick<S3Client, 'send'>, bucket: string, opts?: { source?: string; newId?: () => string }): (e: AuditEntry) => Promise<void>
```

The key layout is identical to `audit-sink.ts` (`audit/<yyyy>/<mm>/<dd>/<tenantId>/<iso with : and . as ->-<uuid>.json`), so objects from both writers already sit together. Differences to know about when switching `api.ts` to `auditWriter(s3, bucket, { source: 'console' })`:
- Each put carries Content-MD5 **and** a SHA-256 checksum.
- Entries are validated before any S3 call and throw `AuditEntryError`: `tenantId` must pass `asTenantId`, `reasonCode` must be lower snake case (all of `REASON_CODES` are), `actor` non-empty, `at` ISO UTC (`...Z`), body at most 32 KB.
- The stored body is a fixed set of fields plus `schema: 1` and `source`; extra properties on the object are dropped.

`test/console.test.ts` imports `auditKey` and `auditWriter` from `audit-sink.js`; point those two imports at `../src/audit.js` when deleting.

## 3. `setTenantState` writes the audit entry first
Old order: engine, profile, audit. If the audit put failed the state had already changed and nothing recorded it, and a retry that skips "already in that state" would never write it. New order: audit (throws, nothing changed), engine, profile; if engine or profile fail a `state:<state>_failed` entry is added and the original error is rethrown. The signature is compatible (`opts.detail` and `deps.now` are optional), and on success there is still exactly one `state:<state>` entry, so the console's tests are unchanged. Please update the sentence in `console/README.md` rule 2 ("engine first, then state, then the audit entry") to "audit entry first, then engine, then state".

## 4. Event field name
`contracts/events/events.schema.json` `tenant.state_changed` names the previous state `previousState` (and requires `actor`). The console emits `previous` and no `actor`. H1 emits the schema's names (`state`, `previousState`, `reasonCode`, `actor: 'billing'`). Suggest the console switch to `previousState` and add `actor`.
