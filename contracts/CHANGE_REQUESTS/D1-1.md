# D1-1: onboarding API keys, errors, status shape, and the onboarding service token (owner: C0, `contracts/` + `packages/shared`)

**From:** D1 (`services/provisioning/src/api/{basics,waitlist,provisioning}.ts`) · **To:** C0. Related: A2-2 (this answers it).

D1 is built and tested against everything below. Nothing here blocks D1; the implementation already behaves this way.

## 1. `contracts/dynamodb/keys.md`: ONBOARDING# items

D1 reads and writes `ONBOARDING#<onboardingId>` with the onboarding API role (`dynamodb:LeadingKeys` `ONBOARDING#*`, see D1-2).

| Entity | PK | SK | Notes |
|---|---|---|---|
| **Onboarding basics** | `ONBOARDING#<onboardingId>` | `BASICS` | businessName (<=120), businessType (<=60), areaText (<=100, what the owner said), `area` `{ areaCode?: "NXX", state?: "TX" }` (what we could resolve), website? (public http(s) only), updatedAt. Overwritten when the owner corrects themselves. |
| **Waitlist entry** | `ONBOARDING#<onboardingId>` | `WAITLIST` | reason (`healthcare`, `region`, `other`), detail? (<=200, owner words kept as data), at. Conditional put `attribute_not_exists(PK)`: the first entry stays. |

Attributes D1 adds to the existing `ONBOARDING#<onboardingId>` / `STATE` item (targeted `UpdateItem`, never a full put):

- `tenantId`: `t_` + 20 hex, generated server-side the first time provisioning starts (`if_not_exists`, so first writer wins and every restart reuses it). It is what the state machine input carries (D5-1).
- `provisioning`: `{ executionName, attempt, startedAt }`. `executionName` is `<onboardingId>` for attempt 1 and `<onboardingId>.<n>` after a failed run (Step Functions never reuses a closed run's name; at most 3 attempts). Never moves backwards (conditional on `provisioning.attempt <= :n`).
- `waitlisted` (bool), `waitlistReason`, `waitlistedAt`.
- `status` values written by D1: `provisioning`, `waitlisted` (the router writes `started`).
- Read by D1, written by D4: `identityStatus` = `pending` (callback consumed the token, owner has not replied YES) or `confirmed` (YES received in the chat that started signup). Anything but `confirmed` returns `409 identity_not_confirmed`, except `channel = webchat`, where the owner signed in with Cognito before the first message.

## 2. `contracts/openapi/onboarding-internal.yaml`: errors and status

Error body for every operation: `{ "code": "<snake_case>", "error": "<same>", "message": "<for logs, not for the owner>" }`. `code` is what `agents/common/api.py` reads; success bodies never contain `error`.

| Operation | Status and `code` |
|---|---|
| all | `401 unauthorized` (no/invalid/expired token), `403 forbidden` (token is for another onboarding), `400 missing_onboarding_id` / `invalid_onboarding_id` / `invalid_json` / `body_too_large`, `404 unknown_onboarding`, `405 method_not_allowed`, `500 internal_error` / `server_misconfigured` |
| `saveBasics` | `200 { saved: true, areaResolved: boolean }`, `400 invalid_basics` |
| `waitlist` | `200 { waitlisted: true, reason }` (repeat calls return the first reason), `400 invalid_reason` |
| `startProvisioning` | `202 { state: "started", alreadyStarted: false, attempt }` first time; `200 { state: "running" or "done", alreadyStarted: true, attempt }` when a run exists; `409 identity_not_confirmed`, `409 waitlisted`, `409 basics_missing`, `409 provisioning_failed` (3 failed attempts), `422 area_needed` (no state or area code known; retry with `preferredAreaCode`), `503 unavailable` |
| `provisioningStatus` | `200`, schema below; `503 unavailable` |

`startProvisioning` request body: `{ "preferredAreaCode"?: "214" | null }`, validated `^[2-9]\d{2}$`, anything else ignored. It is the only field. Tenant id, onboarding id, area and execution name are never read from the body.

`provisioningStatus` 200:

```yaml
state:      { enum: [not_started, running, waiting_on_owner, needs_card, done, failed, waitlisted] }
steps:      { type: array, items: { type: object, required: [step, state], properties: {
              step: { enum: [payment, number, knowledge, profile, agent_name, smoke_call, activate] },
              state: { enum: [pending, started, waiting_owner, done, failed, stopped] },
              messageForOwner: { type: string, description: plain-language line, same voice as onboarding.status } } } }
progress:   { type: array, items: { type: string }, description: 'messageForOwner of every step that has begun, in order' }
waitingOn:  { type: array, items: { enum: [card, facts, hours_and_services, agent_name] } }
testCall:   { enum: [pending, queued, done, failed] }          # A2-2
number:        { type: string, description: 'E.164, only once it is bound to the voice engine' }   # A2-2
numberDisplay: { type: string, example: '(469) 555-0142' }     # A2-2
# forwarding.steps (A2-2) is NOT returned yet: we don't know the owner's carrier and never guess codes (Add-12).
```

`step`/`state` reuse the `onboarding.status` event vocabulary (`number`, `knowledge`, `profile`, `agent_name`, `smoke_call`, `activate`) plus `payment`, which only appears while the card check is the thing speaking up.

## 3. `packages/shared/src/tokens.ts`: the onboarding service token (SEC-22)

The router and agent need to mint what the onboarding API verifies. D1 ships `mintOnboardingToken` / `verifyOnboardingToken` in `services/provisioning/src/api/basics.ts` (same compact HS256 format as `mintTenantToken`; claims `{ onb, aud: "onboarding-api", iat, exp }`; lifetime capped at 1 h; a tool-api token never verifies because the audience differs). Please move both into `packages/shared/src/tokens.ts` and export them; D1 will import from there once it lands. The key is `ONBOARDING_SERVICE_TOKEN` (and optionally `ONBOARDING_SERVICE_TOKEN_PREVIOUS` during rotation) in the runtime secret `1145/<stage>/runtime`; it is now an HMAC signing key, not a bearer value.

## Why
The brief requires "onboardingId from path must match token claim" (threat model SEC-22), the agent needs pinned error codes and a status shape (A2-2), and D5-1 needs the tenant id to be stable across restarts so the ORDER# purchase record keeps protecting the purchase.

## Who else is affected
D1-2 (infra), D1-3 (router/agent/signup callback), A2 (tool prompts read these codes), the owner dashboard (reads `progress` / `steps`).
