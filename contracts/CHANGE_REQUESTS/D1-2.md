# D1-2: onboarding API routes, env and IAM in `ProvisioningStack` (owner: D5, `infra/cdk/lib/provisioning-stack.ts`)

**From:** D1 · **To:** D5 (stack owner). `make synth` is unaffected by D1; these are what the three D1 handlers need at runtime.

## What

1. **Route parameter name.** The stack declares `/internal/onboarding/{id}/...`. The contract and `parse-profile.ts` (D2) say `{onboardingId}` and D2 reads `pathParameters.onboardingId`, so hours and services would 400 today. D1's handlers accept either; please rename to `{onboardingId}` in all eleven routes.

2. **Environment** for every `Api-*` function (the stack's `env` object): add
   - `RUNTIME_SECRET_ID`: the runtime secret `1145/<stage>/runtime` (same variable the router uses). D1 reads `ONBOARDING_SERVICE_TOKEN` (and `ONBOARDING_SERVICE_TOKEN_PREVIOUS`, optional) from its JSON.
   - Already present and used: `TABLE_NAME`, `STATE_MACHINE_ARN`.

3. **IAM** for `Api-basics`, `Api-waitlist`, `Api-provisioning` (D1 handlers):
   - `secretsmanager:GetSecretValue` on the runtime secret (+ `kms:Decrypt` if it uses a CMK).
   - `dynamodb:GetItem`, `PutItem`, `UpdateItem` on the table, `ForAllValues:StringLike` `dynamodb:LeadingKeys` = `ONBOARDING#*`, plus `table.encryptionKey?.grantEncryptDecrypt`. Same pattern as `allowItems` for the steps. Nothing else: D1 never touches `TENANT#*` or route items.
   - `Api-provisioning` only: `states:DescribeExecution` and `states:GetExecutionHistory` on `arn:aws:states:<region>:<acct>:execution:<stateMachineName>:*`. `grantStartExecution` / `grantTaskResponse` do not include them. Without `DescribeExecution`, a repeat start and every status check answer `503 unavailable`. Without `GetExecutionHistory`, status falls back to the run's own state ("Setup is running", done, failed) and logs a warning instead of per-step lines.
   - `Api-provisioning` and the other API functions do not need `events:PutEvents` for D1 (the steps emit `onboarding.status`); leaving the grant is harmless.

4. **State machine input (informational, extends D5-1).** D1 starts the run with
   ```json
   { "onboardingId": "o_...", "tenantId": "t_...", "area": { "areaCode": "214", "state": "TX" },
     "basics": { "businessName": "...", "businessType": "...", "website": "https://..." } }
   ```
   `area.areaCode` and `area.state` are each optional, at least one is present. `basics.website` is optional and already restricted to a public http(s) host (no IP literals, credentials or internal suffixes); `ScrapeKnowledge` should still re-check every fetch and redirect (SEC-17). The execution name is `<onboardingId>` for the first attempt and `<onboardingId>.<n>` after a failed run; every step already keys its side effects by `onboardingId` / `tenantId`, which is why a restart cannot buy a second number (D5 `ORDER#`).

5. **Failure visibility.** `NotifyFailure` is a bare `Pass`, so a failed Build ends the run as SUCCEEDED with `$.error` in the output. D1 reads that (`output.error` or a `NotifyFailure` entry in the history) as "failed" and allows a restart. If `NotifyFailure` becomes a `Fail` state or the state names `CheckPaymentMethod`, `SearchNumber`, `OrderNumber`, `BindEngine`, `ScrapeKnowledge`, `AwaitFactsConfirmed`, `AwaitProfileComplete`, `RenderAgent`, `AwaitAgentName`, `SmokeCall`, `ActivateTenant` change, please tell D1: status progress is derived from them (`STEPS` in `provisioning.ts`).

## Why
Without 1-3 the API cannot authenticate, read or write the onboarding, or look at its own execution. Without 1 the D2 handler cannot read its path parameter.
