# C4-1: widget route item, rate-limit counters and the extra token endpoint answers

From: C4 (customer web chat token). To: C0 (contracts, `packages/shared`, `data-stack.ts`). Also affects T5 (resolver).

## Why
`createCustomerWebchatToken` has to turn a widget key into a tenant, server-side, using a role that can read route items only
(no `TENANT#` data). The key design in `keys.md` has routes for numbers, identities and engine agents, but none for widget keys,
and `grantRouteRead` does not list one. The endpoint also needs a shared place to count requests for its per-IP and per-key limits
(threat model SEC-25, AB-2), and it answers a few statuses the contract does not list yet.

## 1. `contracts/dynamodb/keys.md`: two new items
| Entity | PK | SK | Notes |
|---|---|---|---|
| **Route: widget** | `WIDGET#<widgetKey>` | `ROUTE` | `tid`, `enabled` (boolean, must be `true` to resolve), `businessName` and `agentName` (copies, only so the token endpoint can greet the visitor without reading `TENANT#` data; keep them in step with the profile), `createdAt`. `<widgetKey>` matches `^wk_[A-Za-z0-9]{16,40}$`. Resolver role only. Read by `customer-webchat-token.ts` (C4) and `internal-resolve-widget.ts` (T5). |
| **Rate limit window** | `RATELIMIT#webchat#<bucket>` | `W#<windowStartEpochSec>` | `n` (atomic counter, `ADD`), `ttl` (window end + 1 h). `<bucket>` is `ip:<first 32 hex of sha256(ip)>` or `key:<widgetKey>`. Written by the webchat token role only, never by tenant roles. |

IAM line to add under the table: resolver role (`DataStack.grantRouteRead`) also reads `WIDGET#*`. The webchat token Lambda role additionally
gets `dynamodb:UpdateItem` on `RATELIMIT#*` (see C4-2).

## 2. `packages/shared/src/keys.ts`
Add this next to `numberRoutePk`:

```ts
widgetRoutePk: (widgetKey: string) => `WIDGET#${seg(widgetKey, 'widgetKey')}`,
```

C4 builds the key locally for now
(the value is format-checked against the widget key pattern before it gets near a key) and will switch to the shared builder once it lands.

## 3. `DataStack.grantRouteRead`
Add `'WIDGET#*'` to the `dynamodb:LeadingKeys` list. Without it the token endpoint and the widget resolver both get AccessDenied.

## 4. `contracts/openapi/channels.yaml`: answers that exist but are not documented
Under `/v1/webchat/token` post `responses`, additive:
- `'400'`: body is not `{ "widgetKey": "<string>" }`.
- `'429'`: rate limited per IP or per widget key. Header `Retry-After` (seconds). Body `{ error: rate_limited, message }` where `message` is plain text a visitor can read.
- `'503'`: lookup, secret or signing trouble. Body `{ error: unavailable, message }`.
- `'404'` body is `{ error: unknown_widget, message }` for an unknown, disabled or malformed widget key.
The endpoint also answers `OPTIONS` (CORS preflight, 204) and sends `access-control-allow-origin: *`, because the widget runs on the tenant's own site.

## 5. Greeting
The `greeting` the endpoint returns is the exact line the worker says first in chat (`engines/livekit-agent` `chat_greeting`):
"Hi, this is Ava at Kemi Cuts. I'm the AI assistant, and this chat is saved so the team can follow up. What can I help with?"
The contract example ("Hi, I'm Ava, the AI assistant at Kemi Cuts. What can I help with?") is only an example, but you may want it to match so nobody expects two
different hellos. The widget should show `greeting` once and not repeat the worker's first message when it arrives over the text stream (E5 / widget owner).

## Not changed
Request body, 200 body and room rules from E5-1 are implemented as written (room metadata `{"widgetKey"}`, no `canUpdateOwnMetadata`, agent name `frontdesk`).
The room is created by the signed token's `RoomConfiguration` when the visitor connects, not by a `CreateRoom` call, so a minted but unused token leaves nothing running.
