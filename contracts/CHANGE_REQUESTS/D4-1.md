# D4-1: pending identity binding, deterministic YES / NO, and what the signup contract needs to say (from D4)

From: D4 (Telegram signup link, callback, reverse confirmation). To: C1 (router), D1 (provisioning API), P1/contracts owner, A2 (onboarding agent), Q2 (SEC-20).

D4 is built and tested against local fakes. Nothing below blocks it; this is what the other lanes need to pick up.

## 1. C1 (router): handle the owner's YES / NO in code before any agent runs (SEC-20)

`services/provisioning/src/lib/signup-token.ts` exports `answerPendingBinding(input, bindings, nowSeconds)`:

```ts
answerPendingBinding(
  { onboardingId, channel, channelUserId, text },   // all from the VERIFIED inbound message and its IDENTITY route
  bindings,                                         // createSignupStores({ doc, tableName }).bindings
): Promise<{ handled: false } | { handled: true; outcome: 'confirmed' | 'cancelled' | 'expired'; reply: string }>
```

- It returns `handled: false` (so the router carries on to the agent) unless there is a PENDING binding for that
  onboarding, the text is a plain yes/no (`yes`, `y`, `yep`, `yeah`, `yup`, `no`, `n`, `nope`, `nah`, any case, trailing `.`/`!`),
  and the sender is the same `channel` + `channelUserId` the signup link was sent to.
- On `handled: true`, send `reply` (already passes `@1145/conversation-style`) with the router's own sender. On
  `confirmed` it is also fine, and probably nicer, to let the onboarding agent take the turn too so the conversation keeps
  moving; the agent's tools already treat "confirmed" as the precondition for `start_provisioning`.
- Where in `router.ts`: in `handle()`, right after `lookupIdentity`, when `route.role === 'onboarding'` and `route.onboardingId` is
  set, before `converse(...)`. Use the route's `onboardingId`, never anything in the message.
- How to call it, pick one:
  - **A (preferred, no new infra):** import `createSignupStores` and `answerPendingBinding` from the provisioning lib. The
    router role already has Get/Update on `ONBOARDING#*` (the binding lives at `ONBOARDING#<id>` / `BINDING`, see section 2), so it needs no new grant.
  - **B:** an internal route `POST /internal/onboarding/{onboardingId}/identity-reply` (service token) that wraps the same
    function. D4 does not own an `api/` file for it; whoever adds the route can write the handler in about 15 lines.

Until the router calls it, a YES reaches the onboarding model and nothing is confirmed, so `start_provisioning` correctly
stays at 409 `identity_not_confirmed`. Fail-safe, but the owner is stuck.

## 2. contracts/dynamodb/keys.md and packages/shared/src/keys.ts

New item, next to the router's onboarding record so one IAM prefix (`ONBOARDING#*`) covers both:

| Entity | PK | SK | Notes |
|---|---|---|---|
| **Identity binding** | `ONBOARDING#<onboardingId>` | `BINDING` | `status` (`pending`, `confirmed`, `cancelled`), `googleSub`, `email`, `channel`, `channelUserId`, `pendingUntil` (epoch s, 30 min after sign-in), `confirmedAt`, `cancelledAt`, `claimedAt`, `liveTokenHash` (the one live signup link; a newer link revokes the older). Written only by the signup lambdas with conditional updates; `confirmedAt` is set once and never removed. |

`SIGNUP#<sha256(token)>` / `TOKEN` gains attributes: `onboardingId`, `channel`, `channelUserId`, `exp`, `consumed`, `revoked`, `claimedBy`, `claimedAt`,
`codeVerifier` (PKCE verifier, server-side only), `createdAt`, and `ttl` = `exp` + 1 day (spent links stay readable so a stale link gets a useful answer).

`keys.ts`: add `bindingPk(onboardingId)` (returns `ONBOARDING#<onboardingId>`, validated like the other segments) and `bindingSk()` (returns `'BINDING'`).
D4 builds the key inline until then, and validates the id against `^[A-Za-z0-9_-]{1,64}$`.

## 3. D1 (provisioning API): the 409 rule

`startProvisioning` must return `409 identity_not_confirmed` unless the binding is confirmed. Use:

```ts
import { createSignupStores, isIdentityConfirmed } from '../lib/signup-token.js';
if (!(await isIdentityConfirmed(bindings, onboardingId))) return { statusCode: 409, body: JSON.stringify({ code: 'identity_not_confirmed', message: '...' }) };
```

Web-chat owners sign in with Google before they can chat, so they never get a binding row. D1 decides how the web channel passes the
same gate (for example by trusting the Cognito-authenticated route instead of the binding).
`binding.googleSub` and `binding.email` are what activation needs to create the `MEMBER#` item for the owner.

## 4. contracts/openapi/onboarding-internal.yaml (additive)

- `POST /internal/onboarding/{onboardingId}/signup-link` responses: `200 { sent: true, expiresInMinutes: 15 }` (never a link or token),
  `401 unauthorized`, `404 unknown_onboarding`, `409 link_not_needed` (web chat owner) and `409 already_confirmed`, `502 delivery_failed`. Errors are `{ code, message }`.
- `GET /signup/callback` responses: `text/html` pages, `200` signed in, `400` bad link or sign-in did not finish (link stays usable),
  `409` link already used, `410` link timed out or replaced, `502` could not reach the owner on Telegram. Query: `code` and `state` only.
  Sent with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

## 5. A2 (onboarding agent), informational

`send_signup_link` treats any 4xx/5xx as "the link didn't send". For `409 already_confirmed` the better line is "they're already
signed in, carry on". `r.get("error") == "already_confirmed"` is the code to look for.

## 6. Q2 (threat model)

SEC-20 status once C1 wires section 1: token consumed only after Cognito sign-in succeeds, link previews disabled, `Referrer-Policy: no-referrer`
on the signup pages are done in D4; the deterministic YES / NO is `answerPendingBinding` and needs the router call.
