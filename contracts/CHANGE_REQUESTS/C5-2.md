# C5-2: the referral click log is rate limited (SEC-25), one more item under `REFCLICK#<code>`

From: C5 (referral redirect, `services/channels/src/referral-redirect.ts`). To: P3 (owner of `contracts/dynamodb/keys.md`). FYI: Q2 (threat model F10, SEC-25).

## 1. `contracts/dynamodb/keys.md`: one row next to the C5-1 click items (additive)

| Entity | PK | SK | Notes |
|---|---|---|---|
| Referral click window | `REFCLICK#<code>` | `RATE#<windowStartEpochSec>` | `n` (atomic `ADD`, one per click the redirect was about to write), `ttl` (window end + 1 h). One window is an hour. Past 120 in a window the redirect still sends the visitor on with `ref`, but writes no marker and adds no click. Same partition and IAM prefix as the other click items (`REFCLICK#*`, `UpdateItem`), so no new grant. |

No address is stored anywhere. The per-address limit (10 counted clicks per source address per 10 minutes, across all codes) is kept in the
Lambda container's memory only, keyed by the `sourceIp` API Gateway reports, never by `X-Forwarded-For`.

## 2. Threat model (Q2), for the SEC-25 row
C5 part done: the stage throttle on `GET /r/{code}` (C5-1, in `ChannelsStack`) caps request volume; the handler now caps what reaches the
click log per address and per code. A flood from one address adds at most 10 clicks per 10 minutes per warm container; a flood spread over
many addresses adds at most 120 clicks an hour to one code. Every visitor still gets the redirect. Bots, unknown codes and bad codes never reach
the limiter, so they cannot use up a real visitor's allowance.
