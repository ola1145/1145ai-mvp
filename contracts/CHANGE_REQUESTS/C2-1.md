# C2-1: wire the Telegram webhook function and switch the router to the shared sender

From: C2 (Telegram). To: C1 (owner of `infra/cdk/lib/channels-stack.ts`, `services/channels/src/router-deps.ts`, `services/channels/src/lib/**`).
Answers C1-1 section 3 ("tell C1 the export name").

## 1. `ChannelsStack`: the webhook function needs the runtime secret
`services/channels/src/telegram-webhook.ts` now exports a real Lambda `handler`. It checks `X-Telegram-Bot-Api-Secret-Token`
against `TELEGRAM_WEBHOOK_SECRET` from the runtime secret `1145/<stage>/runtime` (the blob `scripts/secrets/push.sh` writes) and
enqueues to the FIFO queue. Today the `TelegramWebhook` function gets `QUEUE_URL` (good) but neither the secret id nor read
access, so every update would answer 500 until this lands. It fails closed: no secret, no accepted update.

```ts
// constructor, before the `fn(...)` calls: one handle on the runtime secret, shared with buildRouter
const stage: string = this.node.tryGetContext('stage') ?? 'dev';
const runtimeSecret = sm.Secret.fromSecretNameV2(this, 'RuntimeSecret', `1145/${stage}/runtime`);

// replace: const telegram = fn('TelegramWebhook', 'telegram-webhook.ts');
const telegram = nodeFn(this, 'TelegramWebhook', 'services/channels/src/telegram-webhook.ts', {
  timeoutSec: 5,
  env: { ...env, RUNTIME_SECRET_ID: `1145/${stage}/runtime` },
});
runtimeSecret.grantRead(telegram);
```

`buildRouter` should then use the same `runtimeSecret` handle instead of importing the secret a second time. It already has
`inbound.grantSendMessages(telegram)`, which is all the SQS access the webhook needs.

## 2. Router: use `telegram-send.ts` and delete the local copy
`services/channels/src/telegram-send.ts` now exports (same retry rules as `lib/telegram.ts`: 429 waits exactly `retry_after`,
5xx and network errors back off, other 4xx never retry, 4096 character split):

| Export | Use |
|---|---|
| `createTelegramSender({ token, fetchImpl?, sleep?, maxAttempts?, timeoutMs?, maxRetryAfterSeconds? })` | Same config shape as the local one and returns `(chatId, text) => Promise<void>`, so it drops straight into `createSender({ sendTelegram })`. |
| `sendTelegramMessage({ token, chatId, text, silent? })` | The one-shot form named in C1-1. Returns `{ messageIds }`. |
| `TelegramSendError` | `status`, `retryable`, `retryAfterSeconds`, `description`, `partsSent`. Never contains the token. |
| `splitForTelegram`, `TELEGRAM_MAX_LENGTH` | Moved here so `lib/telegram.ts` can go. |

Proposed edit in `router-deps.ts`: `import { createTelegramSender } from './telegram-send.js';` in place of `./lib/telegram.js`, then delete
`lib/telegram.ts` and point the `createTelegramSender` import in `test/channels.test.ts` at `../src/telegram-send.js`.

Differences C1 should know about (all stricter, none change the happy path):
- The chat id must be numeric (`-?\d{1,20}`). A `@channelname` or anything else is refused before any request, so a bad
  value can never turn into a send to somewhere unintended.
- The token must look like a BotFather token before it goes into the URL path.
- A `retry_after` longer than 20 s (configurable with `maxRetryAfterSeconds`) fails fast with `retryable: true` instead of
  sleeping 30 s and trying again, because retrying early only extends Telegram's penalty. SQS redelivery then retries later.
- Link previews are off (threat model SEC-20) and no `parse_mode` is ever sent, as before.
- On a failed later part of a long reply, `error.partsSent` says how many parts already went out.

## 3. Not a change request, but worth knowing
- Message group id on the FIFO queue is `telegram#<from.id>` and the dedup id is `telegram#<from.id>#<update_id>`.
  `InboundMessage.channelMessageId` is the Telegram `update_id`.
- The webhook now also ignores private updates where `from.id` differs from `chat.id`, and answers 405 to non-POST.
- Rotating `TELEGRAM_WEBHOOK_SECRET`: the function caches it for 60 s. See `scripts/telegram/README.md`.
- C6 (`services/notifications`) keeps its own Telegram adapter and reads `telegramBotToken` from the secret `1145/notifications`
  (C6-2), while the router reads `TELEGRAM_BOT_TOKEN` from `1145/<stage>/runtime`. They must hold the same bot token; worth
  unifying on the runtime secret when someone is in `notifications-stack.ts`.
