# C1-1: contract additions for the router (keys, realtime payload, Telegram sender)

From: C1 (router). To: P1/contracts owner, C2 (Telegram), P6 (realtime).

## 1. `contracts/dynamodb/keys.md`: two new router-owned items
The router now writes these (IAM: `dynamodb:LeadingKeys` `IDENTITY#*`, `ONBOARDING#*`, `MSGDEDUP#*` on the router role only).

| Entity | PK | SK | Notes |
|---|---|---|---|
| **Onboarding** | `ONBOARDING#<onboardingId>` | `STATE` | status (`started`), channel, channelUserId, displayName, optional `referralCode` (validated `^[A-Za-z0-9_-]{4,64}$`) and `referrerTid` (looked up from `REFERRAL#<code>`/`OWNER`, never from message text), createdAt. Written in one transaction with the IDENTITY route, conditional `attribute_not_exists(PK)` on the route, so two first messages create one onboarding. |
| **Message dedup** | `MSGDEDUP#<channel>#<sha256(channelUserId\nchannelMessageId)>` | `SEEN` | status `processing` (lease 150 s) then `done`; TTL 2 days. A replayed message id never invokes an agent twice. |

Also documented here because the router depends on it: an IDENTITY route item carries `role` (`owner|staff|onboarding`), `tid` or
`onboardingId`, and tenant state in `tenantState` (or `state`): `provisioning|active|suspended`. Provisioning (D-lane) should keep
`onboardingId` on the route until activation flips it to the tenant.
The referral item should expose the referrer as `referrerTid` (the router also accepts `tid`).

## 2. `contracts/realtime/channels.md`: owner chat reply payload
Replies on `/owners/<sub>/chat` are published as a single event string containing JSON:
`{ "type": "chat.reply", "version": 1, "occurredAt": "<iso>", "data": { "role": "agent", "text": "<reply>", "inReplyTo"?: "<clientMessageId>" } }`.
This is not an EventBridge envelope (there is no tenant yet during onboarding). The web app (owner) should render `data.text`.

## 3. C2: share the Telegram sender
`services/channels/src/lib/telegram.ts` (C1) has a small `createTelegramSender` (retry 429 honoring `retry_after`, retry 5xx, never 4xx,
split at 4096 chars) so replies work before C2 lands. When `telegram-send.ts` exports an equivalent
(`sendTelegramMessage({ token, chatId, text })`), C1 will switch `router-deps.ts` to it and delete the local copy. Tell C1 the export name.
