# D8-1: state machine and IAM changes for the final steps (SmokeCall, ActivateTenant, AwaitOwner, EmitStatus)

**From:** D8 (smoke call, activate, await owner, emit status) · **To:** D5 (`infra/cdk/lib/provisioning-stack.ts`)
**Not blocking:** the four steps are built and tested with fakes. They do nothing useful in dev until this lands.

## What
`provisioning-stack.ts` today gives every step the same shape: 60 s timeout, default retry, no table access for
`await-owner`, and a `NotifyFailure` Pass that still carries `TODO(W1-13)`. The final steps need the following.

### 1. SmokeCall needs minutes, not 60 s
A smoke call rings, talks and ends, up to twice. Give the `smoke-call` Lambda `timeout: Duration.minutes(5)` and the
state `taskTimeout`/Lambda timeout to match. The handler reads `context.getRemainingTimeInMillis()` and shrinks its
per-call wait to fit (never below 15 s), so a shorter timeout still behaves but will often miss a real call.

The default `States.TaskFailed` retry on SmokeCall is harmless (the step counts attempts in DynamoDB, so a re-run can
never ring the owner more than twice in total) but pointless; a short `maxAttempts: 1` is enough.

### 2. Do not activate after a failed smoke call
`smoke-call` resolves `{ ok: false, attempts, reason }` after it has told the owner and opened the triage case; it does
not throw. Add a Choice after SmokeCall:

    SmokePassed:  $.smoke.ok == true  ->  ActivateTenant
                  otherwise           ->  HeldForSupport (Succeed, no further steps)

Without the Choice the execution still stays safe: `activate-tenant` refuses with `SmokeCallNotPassed`
(it checks `$.smoke.ok === true` first and writes nothing), but the execution then shows as failed after two pointless retries.

### 3. Replace `NotifyFailure` with real status messages
Add an `emit-status` Lambda (`steps/emit-status.ts`, same `step()` helper) and use it as a task with a payload that
carries the workflow identity plus what to report:

    { "onboardingId.$": "$.onboardingId", "tenantId.$": "$.tenantId", "step": "number", "state": "failed" }

Suggested wiring: `Catch NoNumberAvailable -> EmitStatus(number, failed)`; any other Build failure ->
`EmitStatus(activate, failed)` ("Something got in the way of switching you on. Our team has been told..."). The
available (step, state) pairs are the ones in `STATUS_COPY` in `emit-status.ts` (every one is style-checked in CI).
Optional progress lines from the state machine (for example `number/done` after BindEngine, `knowledge/waiting_owner`
before AwaitFactsConfirmed, `agent_name/waiting_owner` before AwaitAgentName) use the same payload shape, with
`agentName` added for `agent_name/done`. Give the task `retryOnServiceExceptions` and a 3-attempt retry: a failed save
or publish throws on purpose so the retry sends it again.

### 4. IAM (item-level, by leading key; the stack already has `allowItems`)
All four also need `table.encryptionKey.grantEncryptDecrypt` (already inside `allowItems`).

| Lambda | Actions | Leading keys | Also |
|---|---|---|---|
| `await-owner` | `dynamodb:UpdateItem` | `ONBOARDING#*` | `states:SendTaskSuccess` (via `stateMachine.grantTaskResponse`, as for the API Lambdas) |
| `emit-status` | `dynamodb:PutItem` | `ONBOARDING#*` | `events:PutEvents` on the bus (`bus.grantPutEventsTo`) |
| `smoke-call` | `dynamodb:GetItem`, `UpdateItem`, `PutItem`, `Query` | `TENANT#*` (SMOKE#, TRIAGE#, CALLEND#, PROFILE, MEMBER#), `ONBOARDING#*` (status rows) | `events:PutEvents`; voice engine credentials once the factory exists (D8-3) |
| `activate-tenant` | `dynamodb:GetItem` | `ONBOARDING#*`, `NUMBER#*` | |
| | `dynamodb:UpdateItem` | `TENANT#*` (PROFILE), `IDENTITY#*` (route flip) | |
| | `dynamodb:PutItem` | `ONBOARDING#*` (status row) | `events:PutEvents` |

`IDENTITY#*` and `NUMBER#*` are route partitions (keys.md). The flip is a conditional UpdateItem that only succeeds on
the route that still carries this onboarding's id, or one already flipped to the same tenant.

## Why
The brief's three behaviours (retry once then a friendly status and triage; flip the route and emit
`tenant.provisioned`; status messages in plain words) only reach the owner if the state machine can run them.

## Not requested, for your information
`await-owner` needs no new payload: it keys everything by `onboardingId` and `what`, which `waitOwner` already sends.
The old stub comment about submitting "10DLC brand / WABA as separate executions" is gone on purpose; ADR-0005 removed
those channels, and `activate-tenant` submits nothing to any vendor.
