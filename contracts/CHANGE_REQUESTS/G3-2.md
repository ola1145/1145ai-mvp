# G3-2: alarm on the post-call dead-letter queue (owners: P2 for `bin/app.ts`, P7 for the runbook)

**From:** G3 · **Status:** open, not blocking

## What
`PostCallStack` now exposes `readonly dlq: sqs.Queue`. Events that still fail after the Lambda's two retries (and
events EventBridge could not deliver) wait there for 14 days. Nothing pages anyone yet, because
`ObservabilityStack` only alarms on the queues passed in `dlqs`, and `bin/app.ts` passes none.

## Proposed change to `infra/cdk/bin/app.ts` (P2)
```ts
const postcall = new PostCallStack(app, p('postcall'), { env, data, events });
// ...
new ObservabilityStack(app, p('observability'), { env, dlqs: [postcall.dlq] });
```
(`ObservabilityProps.dlqs` and the `Dlq-<n>` alarm already exist; no change in `observability-stack.ts`.)

## Proposed addition to `docs/runbooks/alarms.md` (P7), under "DLQ"
> **Post-call DLQ** (`PostCallDlq`). A `call.ended` event the post-call Lambda could not finish. The message body is
> either the original event (EventBridge could not deliver it) or a Lambda failure record with the error under
> `responsePayload` and the original event under `requestPayload`. Treat both as data. Fix the cause (usually a G2
> module not deployed yet, Bedrock throttling, or Stripe down), then replay by putting the original event back on the
> bus or invoking the function with it. A call that already finished is a no-op, and a half-finished one resumes at the
> step that failed, so replaying is always safe and never double-counts usage.

## Why
Without the alarm a call that was never billed or never summarised fails silently after the retries run out.
