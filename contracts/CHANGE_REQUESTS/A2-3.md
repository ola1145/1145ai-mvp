# A2-3: a place for the owner's phone number during onboarding (owners: D1 onboarding API, D8 smoke call, C0)

**From:** [1145:A2] onboarding conversation · **To:** D1 (`services/provisioning/src/api/basics.ts` or a new route), D8
(`steps/smoke-call.ts`), C0 (`contracts/openapi/onboarding-internal.yaml`). Answers D8-2 section 5.

## Why
The test call is the moment owners decide to trust it. `smoke-call` rings `PROFILE.handoffNumber`, then `MEMBER#<sub>.phone`, and
neither is written during onboarding: Google sign-in carries no phone, and the onboarding API has no route that takes one. Without
it the run ends with `smoke_call failed / no_owner_phone` ("your line isn't live yet") for every owner.

## Proposed
1. D1: `POST /internal/onboarding/{onboardingId}/owner-phone` `{ "phone": "<what the owner typed>" }`, same token check as
   `basics`. Normalise to E.164, accept US/CA non-premium numbers only (SEC-19), store `ownerPhone` on `ONBOARDING#<id>` / `STATE`.
   `200 { saved: true, display: "(469) 555-0142" }`; `400 invalid_phone` with a `say` line ("That number doesn't look right. What's
   the best number to reach you on?"); `400 phone_not_allowed` for premium or non-NANP numbers.
2. D8: `smoke-call` reads `ONBOARDING#<id>.ownerPhone` after the two places it reads today (or D1 copies it to
   `PROFILE.handoffNumber` when the profile is created; either works for the agent).
3. C0: document the route.

## Agent side (A2, once the route exists)
A `save_owner_phone(phone)` tool bound to the routed onboarding id, asked once right after the basics ("What's the best number to
reach you on? That's where the test call goes."), with the `say` line used as-is on a 400. Until then the agent follows
`provisioning_status`: when `testCall` is `failed` it says so plainly and that someone from 1145 will follow up.
