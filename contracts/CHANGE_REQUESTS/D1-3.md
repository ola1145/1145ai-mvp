# D1-3: callers of the onboarding API: per-invocation token, signup confirmation, tool reactions (owners: A1 agents, D4 signup, C1 router)

**From:** D1 · **To:** A1 (`agents/onboarding/`, `agents/common/api.py`), D4 (`signup-callback.ts`), A2 (onboarding prompt/tool copy)

The onboarding API no longer accepts a static bearer value (threat model SEC-22). It accepts only a short-lived signed token that names the onboarding it is for, and the path id must match.

## 1. A1: mint a token per turn from the routed onboarding id
`onboarding/app.py` builds `HttpApi(url, os.environ["ONBOARDING_SERVICE_TOKEN"])` once per process with the static value. Please mint instead, inside `invoke`, from `payload["onboardingId"]` (router-supplied, not model output), with the existing env value now used as the HMAC key:

```python
import base64, hashlib, hmac, json, time

def mint_onboarding_token(onboarding_id: str, secret: str, ttl: int = 900, now: int | None = None) -> str:
    b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b"=").decode()
    now = int(time.time()) if now is None else now
    h = b64(json.dumps({"alg": "HS256", "typ": "JWT"}, separators=(",", ":")).encode())
    p = b64(json.dumps({"onb": onboarding_id, "aud": "onboarding-api", "iat": now, "exp": now + ttl}, separators=(",", ":")).encode())
    sig = b64(hmac.new(secret.encode(), f"{h}.{p}".encode(), hashlib.sha256).digest())
    return f"{h}.{p}.{sig}"
```

D1 checked this output against its verifier (TypeScript) in both directions. Keep `ttl` at or under 900 s; the API rejects anything that claims to live longer than an hour. The secret must be at least 16 characters (`openssl rand -base64 48` is fine). Until this lands, the deployed agent's static bearer gets `401 unauthorized` from every onboarding route, so land it with or before the stack change in D1-2.

## 2. D4: record the reverse confirmation where D1 reads it
`startProvisioning` returns `409 identity_not_confirmed` unless `ONBOARDING#<id>` / `STATE` has `identityStatus = "confirmed"` (web chat is exempt: the owner signed in with Cognito before the first message). Please write:
- on callback consume: `identityStatus = "pending"`;
- when the owner's YES arrives in the chat that started signup: `identityStatus = "confirmed"`, with a conditional update so a NO or a second account can never flip it;
- on NO: `identityStatus = "rejected"` (D1 treats it like pending).

Targeted `UpdateItem` on `STATE` only (D1 writes other attributes on the same item; see D1-1 section 1).

## 3. A1/A2: how the tools should react to what the API now says
`agents/onboarding/tools.py` treats every error except `identity_not_confirmed` as "setup didn't go through, try again in a minute". D1 returns more specific codes (D1-1 section 2):
- `save_business_basics` gets `areaResolved: false` when the city has no state ("Frisco"). The tool ignores it today and says "Saved." Then `start_provisioning` returns `422 area_needed`. Suggested: when `areaResolved` is false, the agent asks which state, or which area code they'd like for the number, and `start_provisioning(preferred_area_code=...)` passes it.
- `start_provisioning` codes worth their own sentence: `waitlisted` (stop setup, same words as the healthcare reply), `basics_missing` (ask for the basics), `provisioning_failed` (say it failed after a few tries and a person from 1145 will follow up; don't promise a number), `unavailable` (try again shortly).
- `provisioning_status` now returns `state` (`running`, `waiting_on_owner`, `needs_card`, `done`, `failed`, `waitlisted`), `waitingOn` (`card`, `facts`, `hours_and_services`, `agent_name`) and `progress` (plain lines in the 1145 voice). `needs_card` means the owner has to add a card, then the agent calls `start_provisioning` again (that starts attempt 2 under the same tenant). `number` and `numberDisplay` appear only once the number is bound; `forwarding` is not returned yet.

## 4. C1 (informational)
Web chat `ONBOARDING#` records are created with `channel = "webchat"`; D1 relies on that value to treat web owners as signed in. If the router ever creates web onboardings for unauthenticated visitors, tell D1 first.

## 5. D2 (informational, security): `parse-profile.ts` does not check the service token
`POST /internal/onboarding/{onboardingId}/hours` and `/services` (D2) currently trust the path id with no authentication, so anyone who can reach the API can spend Bedrock calls through them. D1's `authorize()` (exported from `services/provisioning/src/api/basics.ts`, later `verifyOnboardingToken` from `@1145/shared`, D1-1 section 3) is what the other routes use: valid token, path id equal to the `onb` claim, otherwise 401 or 403 before any model call. D1 could not change D2's file; please add the same check there.
