# H1-2: Stripe keys in contracts/dynamodb/keys.md, and who writes the customer route

**From:** H1 (Stripe webhook, billing state, audit writer) **To:** contract owner (P3), then provisioning (activation step) and D9 **Status:** open, not blocking (H1 reads these keys through a fake store)

## What
Three additive items in the single table, and a writer for the one the webhook cannot work without.

## Why
`docs/security/threat-model.md` SEC-29 says to dedupe by Stripe event id and to "map Stripe customer → tenant from our record". Neither has a key today. Tenant identity must not come from the event body or Stripe metadata, so the webhook needs a lookup that only our own code writes.

## Proposed change to `contracts/dynamodb/keys.md`

| Entity | PK | SK | Notes |
|---|---|---|---|
| **Stripe event ledger** | `STRIPEEVT#<eventId>` | `SEEN` | `status` `processing` (60 s lease, `leaseUntil` epoch s) then `done` (`outcome`, `doneAt`), `type`, `claimedAt`, `ttl` = 35 days. Claimed with `attribute_not_exists(PK) OR (status = processing AND leaseUntil < now)`. Only verified event ids are claimed. Webhook role only (H1). |
| **Route: Stripe customer** | `STRIPECUST#<customerId>` | `ROUTE` | `tid` (the owning tenant). Written once, conditional `attribute_not_exists(PK)`, by the code that activates the tenant. Never written from a webhook or from Stripe metadata. Webhook role reads only. |

Tenant profile gains (written by the webhook, additive): `billingStatus` (`active` \| `past_due` \| `unpaid` \| `canceled`), `billingEventAt` (Stripe `created`, epoch seconds; only moves forward, so out-of-order events cannot undo newer ones), `billingEventId`. They sit beside, not instead of, `state` / `stateReasonCode` / `stateActor` / `stateUpdatedAt` (H2-2).

IAM: add `STRIPEEVT#*` and `STRIPECUST#*` to the key-family list; neither is readable by the tenant, resolver or console roles. H1-1 lists the exact statements for the webhook role.

## Who writes `STRIPECUST#<customerId>`
D9 creates the Stripe customer during onboarding, when only `onboardingId` exists, so the tenant id is not known yet. Proposal: D9 stores the customer id on `ONBOARDING#<onboardingId>` / `STATE` (for example `stripeCustomerId`), and the provisioning activation step, which already creates the tenant PROFILE and the route items, also puts `STRIPECUST#<customerId>` / `ROUTE` with `tid`, and copies `stripeCustomerId` onto the profile. Until that exists the webhook acknowledges events for unknown customers (outcome `ignored:unknown_customer`, nothing written), so nothing breaks in dev; billing simply has no effect on a tenant that has no route.

## Threat model
With H1 merged, SEC-29 is addressed in code: billing lifts only suspensions whose `stateReasonCode` is `billing`, never replaces an existing suspension reason, dedupes by event id, and maps customer to tenant from `STRIPECUST#`. F9 gap "Dedupe by event id (H1)" and "H1 audit writer is a stub" are closed. Suggest P3 updates those rows and SEC-29's status.
