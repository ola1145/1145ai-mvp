# C1-3: route timezone, the router's message counter, the confirmed sign-in, and what is still open from C1-2

From: C1 (router, `ChannelsStack`). To: P3 (owner of `contracts/dynamodb/keys.md`), D8 (activation), P2 (owner of `infra/cdk/bin/app.ts`),
the owner of `ApiStack`, D1 and D4 (identity gate), A1 and D3 (FYI: `messageId`).

## 1. `contracts/dynamodb/keys.md` (P3)

| Entity | PK | SK | Notes |
|---|---|---|---|
| **Route: identity** (extra attribute) | `IDENTITY#<channel>#<channelUserId>` | `ROUTE` | optional `timezone`: the business's IANA name (`America/Chicago`, `UTC`, `Etc/GMT+5`), at most 64 characters. The router passes it to the copilot payload so "tomorrow" and booking times use the business clock (CR A3-1). Anything that is not an IANA-shaped name is dropped by the router, so a bad value costs the owner nothing but the clock. |
| **Message counter** | `RATELIMIT#chat#<channel>#<first 32 hex of sha256(channelUserId)>` | `W#<windowStartEpochSec>` | `n` (atomic `ADD`, one per accepted message), `ttl` (window end + 1 h). One window is 60 s. Written by the router role only (`dynamodb:UpdateItem`, `LeadingKeys` `RATELIMIT#*`). The web chat token's counters (`RATELIMIT#webchat#...`, CR C4-1) share the prefix. |
| **Onboarding** (two attributes) | `ONBOARDING#<onboardingId>` | `STATE` | `identityStatus` (`confirmed` or `rejected`) and `identityStatusAt` (ISO time), written by the router when the owner answers the sign-in check with a plain YES or NO (SEC-20), in one transaction with the `BINDING` settle (section 4). D4 may also write `pending` when the callback consumes the token (D1-3 section 2); nothing depends on it. |

## 2. D8 (activation): write `timezone` on the identity route
When activation flips the `IDENTITY#` route to the tenant, copy the profile timezone onto it, and update it when the owner changes the
timezone. Until then the copilot falls back to its default (`America/Chicago`), as A3-1 describes. Nothing breaks if it is missing.

## 3. Still open from C1-2 (not C1's files)
These two stop channels from working once deployed. `ChannelsStack` has context fallbacks for the first, but a deploy needs one or the other.
- **P2, `bin/app.ts`:** pass what the router needs, and (CR P7-3) hand the queues and the API to observability. `ChannelsStack` now
  exposes `inbound`, `inboundDlq` and `hooksApiId`.
  ```ts
  const realtime = new RealtimeStack(app, p('realtime'), { env, auth, events });
  const channels = new ChannelsStack(app, p('channels'), { env, data, events, auth, realtime, toolApiUrl: api.url });
  new ObservabilityStack(app, p('observability'), {
    env, alarmEmail: app.node.tryGetContext('alarmEmail'),
    apiIds: [api.apiId, channels.hooksApiId], dlqs: [channels.inboundDlq], fifoQueues: [channels.inbound],
  });
  ```
  Without the first line the router has no `EVENTS_HTTP_DOMAIN` (every web chat reply fails) and no `TOOL_API_URL` (`CONFIRM 1234` fails) unless
  `-c eventsHttpDomain=... -c toolApiUrl=...` is passed at deploy time.
- **`ApiStack` owner:** the router signs tenant tokens with `TOOL_API_TOKEN_SECRET_CURRENT` from `1145/<stage>/runtime`; the tool API still reads its
  own `ToolApiSecret`. Until both hold the same value the tool API rejects every router-minted token (C1-2 section 2).

## 4. D1 and D4: the owner's YES now opens the gate D1 checks (SEC-20)
D1's `startProvisioning` returns `409 identity_not_confirmed` unless `ONBOARDING#<id>/STATE` has `identityStatus = "confirmed"` (D1-3 section 2),
while D4's `answerPendingBinding` only settles `ONBOARDING#<id>/BINDING` (D4-1). Nothing wrote `identityStatus`, so a Telegram owner who
replied YES stayed stuck at 409.

The router now settles both in one `TransactWriteItems` (`services/channels/src/lib/binding.ts`): the `BINDING` update is word for word D4's
`settle` (same condition: still pending, the identity the link went to, inside the window), and the `STATE` update sets `identityStatus`
(`confirmed` on YES, `rejected` on NO), conditional on the onboarding record existing. Either both change or neither does. A write race is
retried through the queue; it is never answered as "timed out". A test runs D1's real `startProvisioning` handler against the same table:
409 `identity_not_confirmed` before the YES, the next gate (`basics_missing`) after it.

- **D1:** nothing to change. Reading `BINDING` through `isIdentityConfirmed` instead would also work, since both items move together.
- **D4:** nothing to change. If `settle` ever changes its condition or attributes, tell C1, because the router repeats it inside the transaction.

## 5. A1 and D3 (FYI): `messageId` in both agent payloads (CR A1-2 section 1)
The router now sends `messageId = "<channel>:<channelMessageId>"` (for example `telegram:812345` or `webchat:c_01J9ZS`) to both agents.
Channel-qualified, because one onboarding can carry on across Telegram and web chat, where ids could look alike. It is left out when it would
not match `[A-Za-z0-9_.:@-]{1,128}` (what the onboarding API accepts for `X-1145-Message-Id`), so D3 stores either a usable id or none.
