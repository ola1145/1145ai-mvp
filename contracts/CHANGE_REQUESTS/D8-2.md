# D8-2: DynamoDB items, profile attributes and one event field the final steps rely on

**From:** D8 · **To:** contracts/keys owner (P3), D1 (status API), D3 (facts and agent-name API), D4/A2 (owner phone)
**Touches:** `contracts/dynamodb/keys.md`, `packages/shared/src/keys.ts`, `contracts/events/events.schema.json`
**Not blocking:** D8 builds these keys inline (as D5 did for `ORDER#`) and swaps to builders when they exist.

## 2. Profile and route attributes written at activation
- `TENANT#<tid>` / `PROFILE`: `state = active` (only from `provisioning` or `active`; never from `suspended` / `over_cap`),
  `numbers = [<e164>]`, `engine`, `activatedAt`, `activatedFrom = <onboardingId>`. `numbers` and `engine` are what the
  console reads (H2-2); without `numbers` a suspend would not find the number route to flip.
- `IDENTITY#<channel>#<channelUserId>` / `ROUTE`: set `role = owner`, `tid`, `tenantState = active`, `activatedAt`; remove
  `onboardingId` (C1-1 says activation flips the route). Only the route that started this onboarding is touched.
- **Gap for D5/D7, not changed by D8:** `render-agent` expects `PROFILE.engineRef` and the console reads `engine` /
  `engineRef`, but `bind-engine` only writes the `NUMBER#` and `ENGINEAGENT#` routes. Someone has to write
  `PROFILE.engineRef` (and the `engineRef` shape differs: render-agent wants an `EngineAgentRef` object, the console
  reads a string or `{ agentId }`). D8 deliberately does not guess.

## 3. Task protocol for D3 (and any API that completes an owner step)
For `facts`, `profile` and `agentName`, read `ONBOARDING#<id>` / `TASK#<what>`:
1. Token present and `status = waiting`: `SendTaskSuccess(taskToken, output)`, then set `status = done`, `result = output`
   and remove `taskToken`.
2. No item, or no token yet (the workflow has not reached the wait): write `status = done` and `result` **without** a token.
   `await-owner` sees `done` the moment it arrives and completes the wait itself, so a quick owner never waits three days.
3. Already `done`: answer success (double submit is harmless).
4. `TaskDoesNotExist` / `InvalidToken` on SendTaskSuccess: a retried state replaced the token; re-read and use the newest.

## 4. Event contract: one optional field
`tenant.provisioned` data gains optional `phoneNumber` (E.164, the tenant's own new business line). This is what C6-2
already asks for ("You're live! Calls to (214) 555-0142 now go to your front desk"); `numberMasked` stays. The event is
not routed to `/tenants/<tid>/live` (live-publisher ignores it), and the live publisher would mask the field anyway.
If you would rather keep the "always masked" rule, say so and D8 drops `phoneNumber`; the notification then says
"Your front desk is answering calls" without the number.

## 5. Owner phone for the smoke call (D1 / A2 / D4)
`smoke-call` reads the number to ring from `PROFILE.handoffNumber` first, then the owner's `MEMBER#<sub>.phone` (C6-1).
The onboarding conversation has to collect it ("What's the best number to reach you on?") and one of those two places
has to be written before SmokeCall runs. With neither, the owner is told plainly, support gets a triage case and no
call is placed.
