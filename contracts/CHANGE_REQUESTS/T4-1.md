# T4-1: wire the direct-edit store into the repo and document updateHours / updateService (owner: T0 / P3 / C0)

T4 implements the owner's direct edits in `services/tool-api/src/lib/profile-writes.ts` and the two handlers
(`admin-update-hours.ts`, `admin-update-service.ts`). The lib exports the `ProfileWriteStore` interface and a DynamoDB
implementation `ddbProfileWrites(doc, table, tenantId)`. Until the repo exposes it, both handlers answer 501
(`profileWritesOf`), and T4's tests use a local fake. Same pattern as T2-1.

## Proposed changes

1. `services/tool-api/src/lib/repo.ts`: add to `TenantRepo`
   ```ts
   import type { ProfileWriteStore } from './profile-writes.js';
   profileWrites: ProfileWriteStore;
   ```
2. `services/tool-api/src/lib/ddb-repo.ts`: in the object returned by `createDdbRepo`, add
   ```ts
   profileWrites: ddbProfileWrites(doc, table, tid),
   ```
   (`import { ddbProfileWrites } from './profile-writes.js'`). `doc` is already the tenant-scoped client, so IAM LeadingKeys applies.
3. `services/tool-api/test/fakes.ts`: give `MemoryRepo` a `profileWrites` store. `MemoryProfileWrites` in
   `test/profile-writes.test.ts` is a working fake (it also makes `getService` read from its own service map).
4. `services/tool-api/src/deps.ts` and `infra/cdk`: `stepUpSecrets` from `STEP_UP_SECRET`, exactly as T2-1 item 4. Price edits fail closed
   (428) until a secret is configured. Nothing else new is needed for IAM: the tenant data role already allows `PutItem`/`UpdateItem` under
   `TENANT#<tid>`, which is what `TransactWriteItems` checks per item.
5. `contracts/openapi/tenant-tools.yaml`:
   - `updateHours` and `updateService`: the 200 response is `AppliedChange` (`{ changeId, kind, summary, messageForOwner }`, `kind` is `hours` or `service`).
   - Add the error responses both can return: `400` (invalid body), `403` (principal not allowed), `404` (`unknown_service`, updateService only),
     `501` (store not wired), `502` (`publish_failed`: the edit is saved but the re-render event was not sent; saving again is safe).
   - `updateHours`: say that `closedDates` replaces the stored list only when the body includes it, and that two windows on one day may not overlap.
   - `updateService`: `x-requires-step-up: [priceCents]` means the field being present at all, including `0`.
   - `x-principals` lists only `owner`, but the shared `principalMayCall` (and the brief) also let `staff` through. The handlers go through
     `requireTenantContext`, so they follow whichever the contract and C0 settle on (see SEC-10 in `docs/security/threat-model.md`). Please
     decide, then either add `staff` here or add a `STAFF_TOOLS` list in `packages/shared`.
6. `contracts/dynamodb/keys.md`: direct edits write the same `AUDIT#<iso>#<changeId>` item as T2-1 (so the audit trail is one list), and
   `updateHours` also sets `PROFILE.timezone` to the new `HOURS.timezone` in the same transaction so the agent's time zone and the schedule never
   disagree. The `PROFILE` update is conditional on the item existing; it never creates a stub profile.
7. `admin.change_applied` (no schema change): direct edits emit it with `{ changeId, kind: 'hours' | 'service', summary, requiresStepUp, appliedBy, via: 'dashboard' }`.
   Their `changeId` (`chg_...`) has no `CHANGECODE#` item, because nothing was proposed. The render-agent subscriber should only use the
   event as a "profile changed, re-render this tenant" signal and read HOURS, PROFILE and SERVICE# items for the actual content.
