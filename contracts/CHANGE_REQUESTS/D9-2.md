# D9-2: wire the card gate in `provisioning-stack.ts` (from D9, card on file before a number)

To: D5 / P2 (owners of `infra/cdk/lib/provisioning-stack.ts`). D9 does not touch infra.

## What
1. **Retry NeedsPaymentMethod on a slow schedule, before the generic retrier.** Today every step gets
   `States.TaskFailed`, 2 attempts, 5 s then 10 s. `CheckPaymentMethod` fails with the error name `NeedsPaymentMethod`
   until the owner has added a card, which can take minutes or hours. With the default retry the whole execution fails
   about 15 seconds after it starts. Step Functions uses the first matching retrier, so these go first:

   ```ts
   const payment = invoke('CheckPaymentMethod', 'check-payment-method', '$.payment', setupPayment, [
     // waiting on the owner: poll every 2 minutes for up to 3 days (2160 attempts, roughly 6.5k of the 25k history events)
     { errors: ['NeedsPaymentMethod'], maxAttempts: 2160, interval: Duration.minutes(2), backoffRate: 1 },
     // Stripe or EventBridge hiccup: a few quick retries
     { errors: ['PaymentUnavailable', 'Lambda.ServiceException', 'Lambda.TooManyRequestsException'], maxAttempts: 5, interval: Duration.seconds(5), backoffRate: 2 },
   ]);
   payment.addCatch(failed, { resultPath: '$.error' }); // exhausted -> NotifyFailure (owner told in plain words)
   ```

   (`invoke()` currently takes one retry config and always appends the `States.TaskFailed` one; it needs to accept a list,
   keeping the generic retrier last.) Each poll is one cheap Lambda call. The step only messages the owner on the first
   poll and after a quiet stretch (default 6 h), so polling every 2 minutes does not nag.

2. **Stripe secret.** New `sm.Secret` `StripeSecret` with JSON key `STRIPE_SECRET_KEY` (a **test-mode** `sk_test_`/`rk_test_`
   key; the code refuses `sk_live_` unless `STRIPE_ALLOW_LIVE=true` is set, which dev and CI must not do).
   `scripts/secrets/push.sh` should write it (`docs/API_KEYS.md` already lists `STRIPE_SECRET_KEY`). Grant read to the two
   Lambdas below only.

3. **Lambda config for the step (`check-payment-method`)**: env `STRIPE_SECRET_ARN`, `TABLE_NAME` and `EVENT_BUS_NAME`
   (the last two already set); grants `stripeSecret.grantRead`, `allowItems(fn, ['dynamodb:GetItem','dynamodb:PutItem','dynamodb:UpdateItem'], ['ONBOARDING#*'])`,
   `props.events.bus.grantPutEventsTo(fn)`.

4. **Lambda config for the API (`Api-payment-setup`)**: today every API Lambda shares one `env`. This one needs its own:
   `STRIPE_SECRET_ARN`, `ONBOARDING_SERVICE_TOKEN_SECRET_ARN` (a secret holding the service token as a bare string or
   `{ "current": "...", "previous": "..." }`; env `ONBOARDING_SERVICE_TOKEN` / `ONBOARDING_SERVICE_TOKEN_PREVIOUS` also work
   but put the token in the template), optional `PAYMENT_SUCCESS_URL` / `PAYMENT_CANCEL_URL` (default `https://1145.ai`).
   Grants: both secrets read, `ONBOARDING#*` Get/Put/Update on the table (see D9-1), no state-machine or events access needed.

5. The workflow input already needs `onboardingId` and `tenantId` (D5-1). The step reads exactly those two.

## Why
Without 1, the gate does not wait for the owner; it ends the onboarding. Without 2 to 4 the Lambdas cannot reach Stripe or
the table and the API answers 500. All of it is mechanical.

## Meanwhile
The step and API are fully tested against fakes (`services/provisioning/test/payment.test.ts`); nothing here needs a
deployed stack. A re-run of the whole workflow in dev should show: no card, status line sent once, execution waiting;
card added on the Stripe page, thank-you line, then SearchNumber starts.
