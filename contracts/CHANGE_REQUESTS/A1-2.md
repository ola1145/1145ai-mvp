# A1-2: what the agents now read from the router, which onboarding routes still reject the new token, and infra for the signing key

**From:** [1145:A1] agent runtime plumbing (integration wave 2) · **To:** C1 (router payloads), D2 / D3 / D4 / D9 (onboarding routes), the infra owner, E (livekit `as_data`), Q2 (threat model)

Nothing here blocks A1: the agents degrade as noted. Item 2 does block onboarding end to end.

## 1. C1: two optional payload fields (`services/channels/src/router.ts`)
The agents read both if present and ignore them if not.

```ts
// owner copilot (router.ts, the `converse(... 'admin' ...)` payload)
{ text, channel, displayName, tenantToken: token, timezone: tenantTimezone }   // PROFILE.timezone, else HOURS.timezone, IANA
// both agents
messageId: msg.channelMessageId
```

- `timezone` gives the copilot the business clock (CR A3-1). Without it the agent assumes `America/Chicago`, which is wrong for any
  tenant outside Central time. `AgentPayload` needs the two optional fields.
- `messageId` is sent by the onboarding agent as `X-1145-Message-Id` (D3-1 section 6), so every facts decision records which owner
  message approved it (SEC-05). Without it decisions are saved with no message id. The API accepts `[A-Za-z0-9_.:@-]{1,128}`; the agent
  drops anything else.

## 2. D2, D3, D4, D9: onboarding routes still compare a static bearer value (blocks onboarding)
`agents/onboarding/app.py` now sends the per-invocation signed token (SEC-22, D1-3 section 1) and no longer sends the static value, so
every route that has not moved to `authorize()` / `verifyOnboardingToken` (`services/provisioning/src/api/basics.ts`) answers 401 to the agent:

| route | file | today |
|---|---|---|
| `GET facts`, `POST facts/decisions` | `api/facts.ts` `serviceTokenAuthorizer` (line ~345) | static compare |
| `POST agent-name` | `api/agent-name.ts` (uses facts.ts `serve`) | static compare |
| `POST signup-link` | `api/signup-link.ts` `serviceTokenAuthorizer` (line ~70) | static compare |
| `POST payment-setup` | `api/payment-setup.ts` `authorized` (line ~277) | static compare |
| `POST hours`, `POST services` | `api/parse-profile.ts` | no auth at all (D1-3 section 5) |

Only `basics`, `waitlist` and `provisioning` accept the token today. Each of the five files needs the same two steps D1 took: verify the
bearer with `verifyOnboardingToken`, then require the path id to equal the `onb` claim (401 before 403, nothing else revealed). The agent
side is ready and tested against the real verifier.

## 3. Infra owner: the onboarding runtime needs its signing key
- Execution role: `secretsmanager:GetSecretValue` (and `kms:Decrypt` on the key) for the runtime secret `1145/<stage>/runtime`. Key
  `ONBOARDING_SERVICE_TOKEN` must be at least 16 characters (the API ignores shorter ones).
- `agents/deploy/plan.py` now launches the onboarding runtime with `RUNTIME_SECRET_ID=1145/<stage>/runtime` and no token on the command
  line. A CDK-managed runtime should set the same env var, or `ONBOARDING_SERVICE_TOKEN_SECRET_ARN` for a dedicated secret.
- Rotation: the API accepts the current and previous key; the agent signs with whichever the secret holds as current and re-reads it
  every 5 minutes.

## 4. E (livekit lane): same `as_data` hole (SEC-04)
`engines/livekit-agent/src/frontdesk/prompts.py` `as_data` still returns `<data>\n{text}\n</data>` with the text unescaped. The agents
version now escapes `<` and `>` (and the fullwidth forms) and takes a `source`; copying `agents/common/api.py` `as_data` is enough.
`services/provisioning/src/lib/sanitize.ts` also still lacks `data` in its role-tag pattern (SEC-04's third location).
