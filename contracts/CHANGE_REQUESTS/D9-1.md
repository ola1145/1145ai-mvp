# D9-1: payment-setup response shape and the `PAYMENT` item (from D9, card on file before a number)

To: C0 (contracts steward). Informational for D1 (provisioning API), D8 (activate / status), H1, H3.

## What
1. `contracts/dynamodb/keys.md`, one new row (router-owned `ONBOARDING#` partition, provisioning role):

| Entity | PK | SK | Notes |
|---|---|---|---|
| **Onboarding payment** | `ONBOARDING#<onboardingId>` | `PAYMENT` | `customerId` (the Stripe customer for this onboarding), `createdAt`, optional `promptedAt` (ISO time the owner was last asked for a card). Conditional put `attribute_not_exists(PK)` so one onboarding has one Stripe customer. No card data of any kind is stored: the card is typed into a Stripe-hosted page. |

   IAM: the `CheckPaymentMethod` step and the `payment-setup` API Lambda need `dynamodb:GetItem|PutItem|UpdateItem` with
   `dynamodb:LeadingKeys` `ONBOARDING#*` (plus the table CMK). The API Lambda also reads `ONBOARDING#<id>`/`STATE` to
   confirm the onboarding exists before it creates anything at Stripe.

2. `contracts/openapi/onboarding-internal.yaml`, `setupPayment` (`POST /internal/onboarding/{onboardingId}/payment-setup`):
   document the responses. The body is not read; the id comes from the path only.

   ```yaml
   responses:
     '200':
       description: One of two shapes
       content:
         application/json:
           schema:
             oneOf:
               - { type: object, required: [status], properties: { status: { const: card_on_file } } }
               - type: object
                 required: [status, url, expiresAt, messageForOwner]
                 properties:
                   status: { const: link_ready }
                   url: { type: string, description: 'Stripe-hosted page where the owner saves a card. Send it in-channel; never read it to the model.' }
                   expiresAt: { type: string, format: date-time }
                   messageForOwner: { type: string, description: 'Friendly line (already conversation-style checked) that contains the url' }
           examples:
             link: { value: { status: link_ready, url: 'https://checkout.stripe.com/c/pay/cs_test_a1B2', expiresAt: '2026-10-07T12:00:00.000Z', messageForOwner: "Before I pick your number, I need a card on file. It's only there to keep fake sign-ups out, and adding it doesn't charge you. You can add it here: https://checkout.stripe.com/c/pay/cs_test_a1B2" } }
             done: { value: { status: card_on_file } }
     '401': { description: 'missing or wrong service token' }
     '404': { description: 'unknown_onboarding' }
     '503': { description: 'unavailable: Stripe is down or throttling; retry' }
   ```

## Why
The route is already in the contract but has no response shape, so the router cannot know what to send. The `PAYMENT`
item is the only state this lane adds. `onboarding.status` needs no change (the step uses `step: number`,
`state: waiting_owner | started`).

## Also (informational)
- **D1 / A2-2**: `startProvisioning` does not need to refuse without a card: the state machine's first step is the gate.
  If the owner agent should say "add a card first" it can read it from `provisioningStatus` (the execution is waiting in
  `CheckPaymentMethod`). A2-2's proposed `402 needs_payment_method` is optional on top of that.
- **H3 / H1 / D8**: the step's output `$.payment` carries `cardFingerprint` and `funding` (e.g. `prepaid`). Trial caps
  (`identityKey`) and referral dedupe should use the fingerprint; `ActivateTenant` is where it can be copied to the
  tenant's billing record. This lane does not write it anywhere else.
- **Delivery of `onboarding.status.messageForOwner`** into the owner's chat during onboarding (no tenant live feed yet)
  is for the consumer (D8 `emit-status` / C-lane). The router can also call `payment-setup` itself and send
  `messageForOwner`; the step notices that (`promptedAt`) and stays quiet instead of sending a second message.
