# E5-1: define the `/internal/resolve/widget` request and how the widget key reaches the chat room

**From:** E5 (worker, web chat) · **To:** contracts owner and C4 (`services/channels`, `customer-webchat-token`)

## What is missing
`contracts/openapi/channels.yaml` lists `POST /internal/resolve/widget` but gives it no request body, and nothing says how
the worker learns the widget key for a `chat-` room. The worker is built against the shapes below. Anything else breaks web chat.

## Proposed change
1. Request body for `/internal/resolve/widget` (SigV4, same as `/internal/resolve/number`):
   `{ "widgetKey": "wk_...", "callId": "<room name>" }`, `required: [widgetKey, callId]`.
   Response is `ResolvedCall` (`contracts/openapi/tenant-tools.yaml`), 404 for an unknown or disabled widget.
2. When `createCustomerWebchatToken` creates the room, set the **room metadata** to
   `{"widgetKey": "<the key the visitor's site sent>"}` (create the room server-side with `CreateRoom` before minting the token,
   or via the token's `RoomConfiguration`). The worker reads only that field.
3. The visitor's token must **not** grant `canUpdateMetadata` / `canUpdateOwnMetadata`, so a visitor cannot rewrite the key
   or any participant attribute mid-chat. Room name `chat-<tid>-<uuid>` is informational only; the worker never reads a tenant
   id from it.
4. Agent dispatch for these rooms uses `agentName: "frontdesk"`, same worker as phone calls.

## Worker behaviour (already implemented in E5)
- Unknown or missing widget key: says a short "this chat isn't set up yet" line and closes the room.
- Resolver outage (timeout / 5xx): says a short "hiccup on our end, try again in a few minutes" line and closes the room.
- Suspended or over-cap tenant: text mode takes a message only.
