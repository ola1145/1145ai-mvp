## 4. `contracts/openapi/tenant-tools.yaml` (C0), additive only
`rescheduleBooking` and `cancelBooking`:
- Request bodies gain optional `customerName` (string, max 120) and `bookedDay` (string, `YYYY-MM-DD`, the calendar day of the appointment in the business's timezone; an ISO date-time is also read in that timezone). With a `verificationCode` they are alternatives: either the code, or name + day.
- 200 responses gain optional `verificationCode` (six digits) and `verificationExpiresAt`, present only when this request had to verify the caller. The code is good for 10 minutes, for this call and this booking only, and lets the agent reschedule then cancel (or the reverse) without asking again.
- Error codes: 403 `verification_required` (nothing usable sent, or the code expired or was never issued for this call), 403 `verification_failed` (name, day or code did not match), 403 `verification_locked` (5 misses for this booking on this call); 404 `booking_not_found`; 409 `booking_cancelled`, `booking_started`, `booking_changed`, `slot_taken`; 422 `invalid_slot` (not on a 15-minute boundary), `outside_hours`, `in_past`.
- The 403 example line "What's the code we sent?" is stale: nothing is sent (ADR-0005) and callers never hear the code. The handlers now say: "Before I change anything, I just need to make sure it's you. What's the name on the booking, and what day is it for?"

## 5. `contracts/dynamodb/keys.md` (C0), additive only
| Entity | PK | SK | Notes |
|---|---|---|---|
| Verification | `TENANT#<tid>` | `VERIFY#<callKey>#<bid>` | `callKey` = first 32 hex of sha256(callId); `codeHash` (never the code), `issuedAt`, `expiresAt` (10 min), `attempts`; `ttl` = expiry + 1 h |
| Reschedule replay | `TENANT#<tid>` | `IDEMP#reschedule:<bid>:<key>` | stored response, TTL 24 h; written in the same transaction as the move |

Booking rows: a reschedule deletes the old `BOOKING#<oldStart>#<bid>` item and puts `BOOKING#<newStart>#<bid>` (the start is in the sort key), adding `previousStart` and `rescheduledAt`. A cancel keeps the item, sets `status = cancelled`, `cancelledAt` and, when given, `cancelReason`, and deletes its `SLOT#` locks. Both happen in one `TransactWriteItems`.

## 6. Customer agent tool definitions (voice/chat lanes)
`reschedule_booking` and `cancel_booking` should take `customer_name` and `booked_day` (`YYYY-MM-DD`) and send them as `customerName` / `bookedDay`, then reuse the returned `verificationCode` for the rest of the call. The agent asks the caller for the name on the booking and the day; it must never fill either from the caller ID or `lookupCaller` (the first name alone is refused by design). Ids and codes stay out of the model's hands where possible (`1145-tenant-isolation`: tools are closures over router-supplied ids).

## 7. Open product gap: how does the customer agent get a booking id?
The paths are `/v1/tools/bookings/{bookingId}/...`, but for a returning caller the agent has no id: `lookupCaller` deliberately returns only a first name and `hasUpcomingBooking` (threat model: "any change that returns more than first name + boolean" is out of tolerance), and `listBookings` is admin-only. The agent only has an id for a booking it created earlier in the same call.

T1 did not invent a route. The W1-11 design says the tool API finds the booking from name + day and issues the code. Proposal for C0/T0: `verifyBooking` (customer-agent), `POST /v1/tools/bookings/verify` with `{ customerName, bookedDay }`, a Query on `TENANT#<tid>` / `BOOKING#<dayStartIso>`..`BOOKING#<dayEndIso>` for that local day, filter confirmed bookings with `nameMatches`, and on exactly one match return `{ bookingId, start, sayToCaller, verificationCode }` through the same `VerificationStore` (counting misses per call, since there is no booking id to count against). Needs a decision on two points: what to say when two bookings match (ask for the time), and whether to also require the booking phone to equal the caller ID (stronger, but a customer calling from another phone would be sent to take-a-message).

## 8. Notes for security review (SEC-24)
- The code is a receipt for a server-side check, not a secret the caller holds: the check itself (surname or full name + booked day) is what stops a spoofed caller ID. Five misses per call and booking lock it for that call. Attempts across calls are not limited here; that belongs with T6's abuse guard (suggest: count `verification_failed` per tenant and caller ID).
- Caller ID is not part of the match (hint, not proof). Requiring it is a one-line addition to `issueVerification` if the product decision in step 7 goes that way.
- Events: `booking.updated` (`bookingId, start, previousStart, serviceId, via`) and `booking.cancelled` (`bookingId, start, serviceId, via, reason?`) already exist in `events.schema.json`; no schema change. `via` is `admin-agent` for the admin agent. Both are published after the transaction commits and a failed publish is logged, not surfaced to the caller (the change already happened).
- DynamoDB Local semantics for `ddbLifecycleStore` (transaction conditions, GSI read after a move) are not exercised yet: T1's tests check the exact `TransactWriteItems` it sends and how cancellation reasons map. T7 could add a `describe.skipIf(!DYNAMODB_LOCAL_ENDPOINT)` block next to `ddb-repo.local.test.ts`.
