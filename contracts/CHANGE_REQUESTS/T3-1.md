# T3-1: expose the report reads on TenantRepo, document paging, and say what writers must store (owner: T0 / P3)

T3 implements the owner reads in `services/tool-api/src/lib/reports.ts`, which exports the `TenantReads` interface and a
DynamoDB implementation `createDdbReports(doc, tid, table)`. Until the repo exposes it, `getSummaryReport`, `listBookings`
and `listConversations` answer 501 with a natural line (`reportsOf`), and T3's tests use a fake DynamoDB document client.

## Proposed changes

1. `services/tool-api/src/lib/repo.ts`: add to `TenantRepo`
   ```ts
   import type { TenantReads } from './reports.js';
   reports?: TenantReads; // make it required once every repo has it
   ```
2. `services/tool-api/src/lib/ddb-repo.ts`: in the object returned by `createDdbRepo`, add
   ```ts
   reports: createDdbReports(doc, tid, table),
   ```
   (`import { createDdbReports } from './reports.js'`). `doc` is already the tenant-scoped client, so IAM LeadingKeys applies
   and a read can only ever see `TENANT#<tid>`. The reads use the base table only (no GSI), and only `Query`/`GetItem`.
3. `contracts/openapi/tenant-tools.yaml`, additive only:
   - `listBookings`: optional query params `limit` (integer, 1 to 200, default 100) and `cursor` (string, opaque). Response
     header `X-Next-Cursor` carries the next page's cursor and is absent on the last page. The body stays the `Booking[]`
     array. `from` and `to` are `[from, to)`. A bare date, or a date-time with no offset, is read in the tenant's timezone;
     a date-time with `Z` or an offset is an exact instant. A bare `to` date includes that whole day.
   - `getSummaryReport`: 200 body
     `{ from, to, timezone, calls, conversations, bookings, cancelledBookings, messages, minutes, sentiment: { positive, neutral, negative }, sayToCaller }`.
     `from`/`to` are calendar days in the tenant timezone, `to` included whole. `bookings` counts confirmed appointments that
     start in the range; `calls` counts voice conversations; `conversations` counts all channels; `minutes` is billable talk time;
     `sayToCaller` is one short natural line the copilot can say as is. Up to 366 days per request.
   - `listConversations`: add optional `cursor`; 200 body `{ conversations: [{ conversationId, startedAt, channel?, summary?, sentiment?, durationSec?, hasTranscript }], nextCursor? }`
     (also sent as `X-Next-Cursor`). The transcript location is never returned; the console API serves transcripts.
4. `infra/cdk` (API Gateway CORS): add `X-Next-Cursor` to the exposed response headers so the dashboard can read it.
5. `contracts/dynamodb/keys.md`, additive, for whoever writes `CONV#` items (post-call, G1/G2): store on each conversation
   `channel` (`voice`, `webchat`, ...), `summary`, `sentiment` (`positive`|`neutral`|`negative`), `transcriptKey`, and, for
   anything with talk time, `durationSec` and `billableSeconds` (the same value `usage.recorded` carries). The reports read
   `billableSeconds` first, then `durationSec`, and count 0 minutes when neither is there. Sort keys for `CONV#`, `BOOKING#`
   and `MSG#` must use `Date.prototype.toISOString()` (UTC, milliseconds, `Z`) so range queries sort correctly.
   Also document that `PROFILE.timezone` is the tenant timezone the reports use (falling back to `HOURS.timezone`).

## Why not in T3's lane

`repo.ts`, `ddb-repo.ts`, the OpenAPI file, `keys.md` and the CDK stack belong to other lanes. Nothing in T3 needs them to land
first: the handlers work today against any repo that has `reports`.

## Not changed

No new dependency, no new IAM action (the tenant role already allows `dynamodb:Query` and `GetItem` on its own partition).
