# H2-3: honour `templatePin` when rendering agents, and CDK assertions for the control-plane stack

**From:** H2 (admin console API) **To:** whoever owns agent rendering (`services/provisioning/src/steps/render-agent.ts`), and P4 (`infra/cdk/test`) **Status:** open, not blocking

## What
1. The template rollout and agent render step must treat `PROFILE.templatePin = { template, version }` as an override:
   a pinned tenant stays on that version and is skipped by canary and fleet-wide rollouts until the pin is removed.
2. P4 adds assertion tests for `ai1145-<stage>-controlplane` in `infra/cdk/test`.

## Why
The console records the pin (and audits it) but does not re-render agents; that belongs to the rendering lane.
Without (1), pinning has no effect on what callers hear.

## Proposed change
1. In the render step, read `templatePin`; if present, load `TEMPLATE#<template>` / `V#<version>` instead of the
   current stable version. Do not write `templateVersion` from the console side: the renderer sets it after it renders.
2. Assertions worth having (all verified by hand against the synthesized template today):
   - The `/console/{proxy+}` routes (GET, POST, PUT) use `AuthorizationType: AWS_IAM`; `/stripe/webhook` stays `NONE`.
   - The console Lambda role has no `dynamodb:*`; `dynamodb:Scan` is the only action without a `LeadingKeys` condition.
   - The tenant bucket grant is limited to `tenants/*`.
   - Outputs `ConsoleApiUrl` and `ConsoleInvokePolicyArn` exist.
