# P4-2: NotificationsStack grants the whole table without a LeadingKeys condition (owner: C6)

**From:** P4 (CDK assertion tests) · **To:** C6 (`infra/cdk/lib/notifications-stack.ts`) · **Contract change:** no · **Blocking:** no

## What
`NotificationsStack` calls `props.data.table.grantReadWriteData(fn)`. That adds an Allow with no condition on the table and
`index/*` for these actions: `BatchGetItem, Query, GetItem, Scan, ConditionCheckItem, BatchWriteItem, PutItem, UpdateItem,
DeleteItem, DescribeTable, GetRecords, GetShardIterator`. The stack then adds a Deny for the item actions where
`ForAnyValue:StringNotLike dynamodb:LeadingKeys` is `TENANT#*`.

## Why it matters
The comment says the dispatcher "can never read route items (NUMBER#, IDENTITY#, SIGNUP#...)". That holds for GetItem,
Query, PutItem and the other item actions, but not for `Scan`:

- IAM only fills in `dynamodb:LeadingKeys` for calls that name a partition key. A Scan names none, so the key is absent.
- `ForAnyValue` is false when the key is absent, so the Deny does not apply to Scan.
- Nothing else stops it, so the dispatcher role can `Scan` every partition: all tenants, and the route items.

I could not run IAM from here, so please confirm with the IAM policy simulator in dev (`dynamodb:Scan` on the table, no
context keys: expect "allowed" today). Either way, the same rule holds for the other LeadingKeys policies in this repo:
a statement that lists `Scan` is not limited by a `ForAllValues` LeadingKeys condition either, because `ForAllValues` is true
when the key is absent. `infra/cdk/test/iam-isolation.test.ts` now checks both.

The dispatcher only uses `GetItem`, `Query`, `PutItem` and `DeleteItem` (`services/notifications/src/store.ts`), so it does
not need Scan, BatchWriteItem, UpdateItem or the stream actions at all.

## Proposed change
Replace the `grantReadWriteData` call with named actions and a condition, the way the other stacks do it. The Deny can stay
as a second layer.

```ts
// before
props.data.table.grantReadWriteData(fn);

// after
fn.addToRolePolicy(new iam.PolicyStatement({
  actions: ['dynamodb:GetItem', 'dynamodb:Query', 'dynamodb:PutItem', 'dynamodb:DeleteItem'],
  resources: [props.data.table.tableArn],
  conditions: { 'ForAllValues:StringLike': { 'dynamodb:LeadingKeys': ['TENANT#*'] } },
}));
props.data.table.encryptionKey?.grantEncryptDecrypt(fn);
```

Update the comment too: the condition, not the Deny, is what keeps the dispatcher off route items.

## What P4 did meanwhile
`iam-isolation.test.ts` lists this grant in `ACCEPTED_TABLE_GRANTS` so the suite is green, and caps it at the actions above:
adding another action to the dispatcher fails the test. After this change lands the entry becomes unused (nothing fails);
P4 will delete it in a follow-up.
