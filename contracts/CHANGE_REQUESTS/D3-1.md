# D3-1: what facts review and agent naming need from other lanes (D1, D5, D6, D8, A2, C0)

D3 (`services/provisioning/src/api/facts.ts`, `agent-name.ts`) is built and tested against local fakes. It works
without any of this, but the owner steps only finish end to end once these small pieces exist. Nothing here renames
or removes an existing key or field (additive only).

## 1. Record shapes D3 reads and writes (C0: `contracts/dynamodb/keys.md`)

`ONBOARDING#<onboardingId>` / `STATE` gains these attributes (the row already exists, written by the router):

| Attribute | Written by | Meaning |
|---|---|---|
| `tenantId` | D1 (start provisioning), once, server-side | Where D3 looks for `FACT#` items and `PROFILE`. D3 never takes a tenant from the path, query or body. Absent until provisioning starts; D3 then returns an empty facts list and keeps a name on this record only. |
| `taskTokens.facts`, `taskTokens.profile`, `taskTokens.agentName` | D8 `await-owner` | The `$$.Task.Token` of the waiting step. D3 removes the one it used. |
| `factsShown` (list of fact ids), `factsShownAt` | D3 | Ids in the latest listing. Only these can be approved (SEC-05). |
| `factsDecision` `{ at, approved, rejected, heldBack, messageId? }` | D3 | Last decision summary. |
| `factsCompletedAt`, `agentNameLockedAt` | D3 | The step was completed (idempotency marker). |
| `agentName`, `agentNamedAt` | D3 | The chosen name. |

`TENANT#<tid>` / `FACT#<fid>` gains `decision` (`approved` or `rejected`), `decidedAt`, `decidedVia` (`onboarding-agent`)
and, when the caller sends it, `decidedMessageId` (the owner's channel message id, for the audit trail in threat-model F3 "R").
D3 also reads optional `flags` (list of names from `sanitize.ts`) and `createdAt`. `fid` must match `^[A-Za-z0-9_-]{1,64}$`
(no `#`, which `keys.factSk` already enforces). Existing attributes are untouched; `verified` is only ever set to true by D3.

`TENANT#<tid>` / `PROFILE` gains `agentName` (D3 sets it with a condition that PROFILE already exists, so it never
creates a half-empty profile). D7's `ProfileSnapshot.agentName` already expects this attribute.

## 2. D8 `await-owner.ts`: store the token, then check whether the owner already answered

Input is `{ token, onboardingId, what }` with `what` = `facts`, `profile` or `agentName` (as in `provisioning-stack.ts`).

1. Store the token: `SET taskTokens = if_not_exists(taskTokens, :empty)` then `SET taskTokens.<what> = :token` (two updates, or
   one with a map merge; D3's `markStepDone` does `REMOVE taskTokens.<what>` conditioned on the same token).
2. Read the record again (consistent). If the owner already answered, finish at once with `SendTaskSuccess`:
   - `what = facts`: `factsDecision` exists, or `factsCompletedAt` is set. Output `{ approved, rejected, heldBack }` from `factsDecision`.
   - `what = agentName`: `agentName` exists. Output `{ agentName }`.
3. Why: in chat the owner often answers before the workflow reaches the wait step (scrape still running, or naming before
   RenderAgent finished). D3 saves the answer and reports `workflow: "not_waiting"`; the step must pick it up. D3 re-reads the
   record after saving, so when the token lands in between, one side or the other always completes the step. Calling
   `SendTaskSuccess` twice is harmless (D3 treats `TaskDoesNotExist`, `TaskTimedOut` and `InvalidToken` as already done).

## 3. D5 `provisioning-stack.ts` (state machine and API wiring)

a. **The two API Lambdas have no table access today.** `Api-facts` and `Api-agent-name` need, scoped like the step Lambdas
   with `dynamodb:LeadingKeys` in `['ONBOARDING#*', 'TENANT#*']`:
   `dynamodb:GetItem`, `dynamodb:Query`, `dynamodb:UpdateItem` (the facts decisions run as one `TransactWriteItems`, which
   needs `UpdateItem` on the same keys), plus the table CMK (`encryptionKey.grantEncryptDecrypt`). `grantTaskResponse` is already there.
   They act as a service on behalf of one onboarding, not as a tenant, so ADR-0003's tenant role does not apply; the leading-key
   condition is the guard.
b. **Service token.** Both handlers read `ONBOARDING_SERVICE_TOKEN_SECRET_ARN` (Secrets Manager; the current and previous
   versions are both accepted so rotation never locks the agent out; the value is the bare token or JSON with key
   `ONBOARDING_SERVICE_TOKEN`) and fall back to `ONBOARDING_SERVICE_TOKEN` for local runs. Please add the env var and
   `secret.grantRead(fn)` for every Lambda in the `routes` loop (D1, D4 and D9 need the same). SEC-22 will replace the
   static token with a per-invocation token; D3's `authorize(token, onboardingId)` hook is where that check goes.
c. **The chosen name never reaches the engine.** The chain is `RenderAgent` then `AwaitAgentName` then `SmokeCall`, so the
   name set in `AwaitAgentName` is saved on `PROFILE.agentName` but never rendered into the agent before the smoke call.
   `render-agent.ts` already says it should re-run after `AwaitAgentName`. Add a second `RenderAgent` (for example
   `RenderAgentFinal`, same Lambda, `$.agentFinal`) between `AwaitAgentName` and `SmokeCall`.
d. Route parameter: the stack names it `{id}`, the contract `{onboardingId}`. D3 accepts both, so no change needed; mentioned so
   nobody "fixes" one side and breaks the other.

## 4. D1 `provisioning.ts` (start provisioning)

Write `tenantId` to `ONBOARDING#<id>` / `STATE` when the execution starts (conditional, so a second start keeps the first value),
in the same place the state machine input gets it (see D5-1). D3 will not read a tenant from anywhere else.

## 5. D6 `scrape-knowledge.ts`

Store each candidate as `TENANT#<tid>` / `FACT#<fid>` with `verified=false`, `flaggedInstructionLike` (true when `flags` is
non-empty), `flags` (the names `toCandidates` returns) and `createdAt`. D3 also re-checks the text itself, so a missing flag
never lets an instruction-like fact through, but the stored flags give the owner the better plain-words reason.

## 6. A2 `agents/onboarding/tools.py` and `agents/common/api.py`

- Pass the inbound channel message id on the decision call as the header `X-1145-Message-Id` (D3 stores it with each decision).
  `HttpApi.post` has no per-call headers today, so this needs a small `headers` argument.
- `confirm_facts` now returns `heldBack: [{ id, reason }]` for flagged facts that were not approved. The tool should tell the
  owner plainly that those stay out and why (`reason` is already plain words), instead of saying "Recorded." Held-back facts stay
  pending and are listed again by `facts_to_confirm` (flagged first); the owner can reject them, and approving them in chat is
  refused by design (SEC-05: they are approved in the dashboard).
- `facts_to_confirm` also gets `reason` on flagged facts and a `flagged` boolean. One fact per question (SEC-05).
- A 400 `fact_not_shown` means the model decided on an id it had not listed in this conversation turn: call `facts_to_confirm` again.
- A 409 `fact_changed` means a fact changed while saving: list again, confirm again.

## 7. C0 `contracts/openapi/onboarding-internal.yaml` (documentation only, additive)

Add request and response schemas for `listFacts`, `decideFacts` and `nameAgent`, the optional `X-1145-Message-Id` header,
and the error codes above (`fact_not_shown`, `unknown_fact`, `fact_changed`, `not_started`, `invalid_name`, `already_named`).
The responses are:

```
GET facts            200 { facts: [{ id, text, source, flagged, status: pending|approved|rejected, reason? }] }
POST facts/decisions 200 { approved: [id], rejected: [id], heldBack: [{ id, reason }], workflow: completed|already_done|not_waiting }
POST agent-name      200 { name, profileUpdated, workflow: completed|already_done|not_waiting }
```

## Notes for reviewers
- Unsure counts as rejected: an id in both lists is rejected. Rejecting needs no prior listing (it can only make the receptionist say less).
- Facts approved from chat can never be flagged ones, in the handler and again in the DynamoDB condition of the write.
- After the agent-name step has completed, a different name gets a 409 with a friendly line; the same name again is a no-op.
