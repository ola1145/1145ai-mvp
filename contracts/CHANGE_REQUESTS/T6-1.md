# T6-1: document the 429 and the RATE# items, share the tenant doc provider, tell the agents what a 429 means

**From:** T6 (rate limiting and abuse guard for the tool API). **Needs:** C0 (contracts), T0 (`lib/ddb-repo.ts`), the lanes that call the tool API (voice worker, AgentCore agents, ElevenAgents tool config), P-lane for the outer throttle.

## What T6 shipped (all in owned files)
- `lib/rate-limit.ts`: DynamoDB token bucket (`createLimiter`, `ddbBucketStore`), the request guard (`createRequestGuard`, `prodRequestGuard`), policies, the 429 lines.
- `lib/http.ts`: `handle(fn, opts?)` now runs a `RequestGuard` before the handler and reports the outcome after it. With no options it uses the process-wide guard (`setRequestGuard`) or, if neither is set, the production limiter, which switches itself on when the Lambda has `TENANT_DATA_ROLE_ARN` (every deployed tool API function does) and is off in unit tests. `RATE_LIMIT_DISABLED=1` is the emergency off switch. No handler file had to change.

Behaviour: the identity is the verified one (Cognito claim, engine secret + agent id, tenant token), the bucket is `TENANT#<tid>` / `RATE#<principal>`, a refusal is a 429 with `Retry-After` and a natural `sayToCaller`, and any limiter failure or a check slower than 120 ms lets the request through.

## 1. `contracts/openapi/tenant-tools.yaml` (C0), additive only
Add a reusable response and reference it from every tool operation (customer, admin and dashboard routes; not `/internal/*`):
```yaml
components:
  responses:
    RateLimited:
      description: Too many requests for this tenant and principal, or too many failed verification attempts. The handler did not run.
      headers:
        Retry-After: { schema: { type: integer, minimum: 1 }, description: Seconds until a retry can succeed. }
      content:
        application/json:
          schema:
            allOf:
              - $ref: '#/components/schemas/Error'
              - { type: object, properties: { retryAfterSec: { type: integer, minimum: 1 } } }
          examples:
            busy: { value: { code: rate_limited, message: too many requests, retryAfterSec: 2, sayToCaller: "Things are a little busy on my end right now. Give me a few seconds and try again." } }
            verification: { value: { code: verification_throttled, message: too many failed verification attempts, retryAfterSec: 540, sayToCaller: "I can't pull that booking up from here, sorry. Let me take a message so the team can sort it out with you." } }
```
Codes: `rate_limited` (any route) and `verification_throttled` (only requests that carry `verificationCode`, `customerName` or `bookedDay`, from the customer agent).

## 2. `contracts/dynamodb/keys.md` (C0), additive only
| Entity | PK | SK | Notes |
|---|---|---|---|
| Rate bucket | `TENANT#<tid>` | `RATE#<principal>` | `tokensMilli` (thousandths of a token), `at` (ms), `v` (compare-and-set version), `ttl` = time to refill completely + 1 min. One per tenant and principal (`customer-agent`, `admin-agent`, `owner`, `staff`) |
| Failed-verification bucket, caller | `TENANT#<tid>` | `RATE#vfail#caller#<hash>` | same attributes; `hash` = first 32 hex of sha256(`<tid>:<callerE164>`), never the number |
| Failed-verification bucket, tenant | `TENANT#<tid>` | `RATE#vfail#tenant` | same attributes; backstop against a guesser who rotates caller IDs |

IAM: no change. The tenant data role already allows `GetItem` and `PutItem` on `TENANT#<tid>` and the table's TTL attribute is `ttl`. The tool API execution role needs nothing new either (it already may `sts:AssumeRole` the tenant role).

## 3. `lib/ddb-repo.ts` (T0)
Export the provider that `ddbRepoFor` uses:
```ts
export const tenantDocFor = prodProvider; // (tid) => Promise<DynamoDBDocumentClient>
```
T6 then drops its own `prodDocFor` in `rate-limit.ts` (marked `TODO(CR T6-1)`) and reuses the cached credentials. Until then a cold container pays one extra AssumeRole per tenant on its first request; the guard's 120 ms budget bounds what that can cost the caller (it lets the request through).

## 4. Callers of the tool API (voice worker, AgentCore agents, ElevenAgents webhook tools)
On a 429, say the returned `sayToCaller` once, wait `Retry-After` before the same tool is tried again, and do not loop on it. A model that retries a 429 immediately is the thing the limiter exists to stop. Defaults (per tenant, per principal): customer agent burst 30, 5/s; admin agent 20, 2/s; owner and staff 40, 5/s (`DEFAULT_POLICIES`). Expect to tune them from the bench numbers.

## 5. T1 (caller verification), nothing to change
This is the cross-call limit T1-1 section 8 asked for. For the customer agent only, requests that carry `verificationCode`, `customerName` or `bookedDay` are refused with 429 `verification_throttled` once the caller number (8 misses, one token back every 10 minutes) or the tenant (30 misses, one back every 2 minutes) has run out. A miss is a response with code `verification_failed` or `verification_locked`. Requests without those fields (taking a message, say) are never held back. If T1 renames a field or code, or `verifyBooking` (T1-1 section 7) uses other field names, update `VERIFICATION_FIELDS` and `VERIFICATION_FAILURE_CODES` in `rate-limit.ts`; the test names both.

## 6. P-lane: the outer fence
The guard only counts requests it can attribute to a verified tenant. Unauthenticated floods (bad tokens, no token) still reach the Lambda and are answered 401 by the handler. A default stage throttle on the HTTP API (and the WAF rate rule already planned for the hooks API in W1-10) is the right fence for those. Not done here: per-call buckets (a looping agent can use up its tenant's customer-agent burst for other concurrent calls of the same tenant, but never another tenant's).
