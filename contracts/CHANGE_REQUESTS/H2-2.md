# H2-2: tenant index in contracts/dynamodb/keys.md, and the profile/route fields the console relies on

**From:** H2 (admin console API) **To:** contract owner (P3), then provisioning (W1-13) **Status:** open, not blocking

## What
1. A way to list tenants without scanning the table.
2. Confirmation (or correction) of the attribute names the console reads and writes.

## Why
`GET /console/tenants` has no key to query, so it scans the table for `SK = PROFILE` rows. That is fine for a few
dozen tenants in dev and gets slower and dearer as the single table grows. The console also has to find a tenant's
phone numbers to flip their routes and to list them for release, and `keys.md` does not say where they live.

## Proposed change to `contracts/dynamodb/keys.md`
1. Tenant profile gains `GSI1PK = TENANTS`, `GSI1SK = <tid>`, written by provisioning when it creates the profile.
   The console then queries GSI1 for `TENANTS` and drops the Scan permission. The IAM leading-key rule in the
   Tenant role is unaffected (`TENANTS` is not a `TENANT#` key). Existing profiles need a one-off backfill.
2. Document these profile attributes (the console assumes them today):
   - `numbers`: array of E.164 strings owned by the tenant.
   - `engine` (`livekit-telnyx` | `elevenlabs`) and `engineRef` (the agent id string, or `{ agentId }`).
   - `state`: `active` | `suspended` | `over_cap`, plus `stateReasonCode`, `stateActor`, `stateUpdatedAt` (console writes these).
   - `templatePin`: `{ template, version, reasonCode, actor, at }`, set and removed by the console.
3. Route items (`NUMBER#`, `ENGINEAGENT#`) carry `tid` (the owning tenant). The console reads it before deleting a route
   and conditions route-state updates on it. Say so in the table.
4. `USAGE#<yyyy-mm>` stores the counter as `billableSeconds` (the console also accepts `seconds`).
5. `CONV#...` items carry `transcriptKey` under `tenants/<tid>/transcripts/` (the console refuses any other prefix).
