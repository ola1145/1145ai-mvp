# P5-1: index the MEMBER# item by Cognito sub

**From:** P5 (auth) · **To:** owner of `contracts/dynamodb/keys.md` and `packages/shared/src/keys.ts`, and whoever writes `MEMBER#` items (onboarding/provisioning)

## Why
The pre-token trigger only knows the Cognito `sub`, not the tenant. `MEMBER#<sub>` lives under `TENANT#<tid>`, so there is
no way to find it without the tenant id (a scan would cross tenants). The trigger needs one indexed lookup.

## Proposed change
1. In `contracts/dynamodb/keys.md`, on the "Owner/staff" row, add: `GSI1PK = MEMBER#<sub>`, `GSI1SK = TENANT#<tid>`.
   Add the same under the GSI1 line: "member by Cognito sub".
2. In `packages/shared/src/keys.ts` add:
   ```ts
   memberGsi1: (sub: string, tid: string) => ({ GSI1PK: `MEMBER#${seg(sub, 'sub')}`, GSI1SK: `TENANT#${seg(tid, 'tid')}` }),
   ```
3. Every writer of `MEMBER#<sub>` items must set those two attributes and a `role` attribute (`owner` or `staff`).
4. Tenant `PROFILE` must carry `state` as `active | suspended | over_cap` (already in the contract).

## Notes
- The tenant data role's `LeadingKeys` condition does not match `MEMBER#*`, so tenant-scoped code cannot read the index
  entry of another tenant. Only the pre-token Lambda is granted `dynamodb:Query` on GSI1 for `MEMBER#*`.
- Claim names the tool API / app can rely on: `custom:tenant_id`, `custom:role` (`owner|staff`), `custom:state` (`active|suspended|over_cap`).
  Consumers (P2 tool-api, owner app) should refuse writes when `custom:state` is `suspended`.
- Until this lands, the trigger finds no member and issues tokens without a tenant claim (fails closed).
