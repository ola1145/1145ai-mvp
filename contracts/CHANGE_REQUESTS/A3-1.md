# A3-1: give the copilot the business clock (for A1, `agents/admin/app.py`)

**From:** [1145:A3] owner copilot conversation quality · **To:** [1145:A1] AgentCore runtime plumbing

## Why
Owners ask "what's tomorrow look like?" and "close us on Thanksgiving". The copilot has to turn that into
YYYY-MM-DD / ISO date-times for its tools, and booking results now come back with times in words ("tomorrow at 9am")
computed against the business's clock. Today `app.py` gives the agent neither today's date nor the business timezone,
so "tomorrow" is a guess and UTC booking times are shown on the UTC clock.

## Proposed change (agents/admin/app.py only)
1. Pass a tz-aware clock into the tools. `make_admin_tools` already accepts it (A3, backwards compatible):
   ```python
   from datetime import datetime
   from zoneinfo import ZoneInfo
   tz = ZoneInfo(payload.get("timezone") or "America/Chicago")   # router puts the tenant's tz in the payload
   tools = [tool(fn) for fn in make_admin_tools(api, now=lambda: datetime.now(tz))]
   ```
2. Append one line of context to the system prompt per invocation (not owner text, so no injection risk):
   ```python
   system = SYSTEM + f"\n\nRight now it's {datetime.now(tz):%A, %B %-d, %Y, %-I:%M %p} at the business ({tz.key})."
   ```
3. The skill `1145-agentcore-agents` says Haiku for the copilot; `MODEL_ID` currently defaults to Sonnet 4.5.

The router (channels lane) would need to include `timezone` in the copilot payload; until it does, the default above
keeps behaviour no worse than today.

## Until then
A3 tests inject a fake clock (`make_admin_tools(api, now=...)`). Without it the tools default to UTC.
