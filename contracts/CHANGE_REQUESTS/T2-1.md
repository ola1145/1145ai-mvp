# T2-1: expose the change store on TenantRepo and wire step-up secret (owner: T0 / P3)

T2 implements propose/apply in `services/tool-api/src/lib/changes.ts`, which exports the `ChangeStore` interface and a
DynamoDB implementation `ddbChangeStore(doc, table, tenantId)`. Until the repo exposes it, both handlers answer 501
(`changeStoreOf`), and T2's tests use a local fake.

## Proposed changes

1. `services/tool-api/src/lib/repo.ts`: add to `TenantRepo`
   ```ts
   import type { ChangeStore } from './changes.js';
   changes: ChangeStore;
   ```
2. `services/tool-api/src/lib/ddb-repo.ts`: in the object returned by `ddbRepoFor`, add
   ```ts
   changes: ddbChangeStore(doc, TABLE, tid),
   ```
   (`import { ddbChangeStore } from './changes.js'`). `doc` is already the tenant-scoped client, so IAM LeadingKeys applies.
3. `services/tool-api/test/fakes.ts`: give `MemoryRepo` a `changes` store (T2's `MemoryChangeStore` in `test/changes.test.ts` can be moved there).
4. `services/tool-api/src/deps.ts`: add `stepUpSecrets` to `prodDeps()` reading `STEP_UP_SECRET` (current + previous) from the
   tool-api secret, same pattern as `tokenSecrets`. `ChangeDeps` in `changes.ts` already accepts it; it falls back to
   `process.env.STEP_UP_SECRET`, and fails closed (428) when no secret is configured.
5. `contracts/dynamodb/keys.md`: document two tenant-partition items:
   - `TENANT#<tid>` / `CHANGECODE#<4 digits>`: pending/applied change; the code is the sort key so a conditional put keeps codes
     unique among open changes; `ttl` = expiry + 1 day.
   - `TENANT#<tid>` / `AUDIT#<iso>#<changeId>`: audit entry per applied change.
6. Step-up token format (for the dashboard issuer, U1 / `/dash` auth): compact HS256 JWS signed with `STEP_UP_SECRET`, claims
   `{ tid, sub?, aud: 'step-up', iat, exp }`, TTL about 5 minutes. `mintStepUpToken` / `verifyStepUpToken` in `changes.ts` define it. T4
   (`admin-update-service.ts` price edits) should reuse `verifyStepUpToken`.
7. `contracts/events/events.schema.json`: add a `$defs` entry for `admin.change_applied` with data
   `{ changeId, kind, summary, requiresStepUp, appliedBy, via }`.
8. `contracts/openapi/tenant-tools.yaml`: the 201 response of `proposeChange` also returns `messageForOwner`; applyChange 200 returns
   `{ changeId, kind, summary, messageForOwner }`.
